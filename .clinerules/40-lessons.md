# Грабли и уроки харнесса

Файл действует всегда. Сюда дописывается знание, добытое **по ходу работы**.

Правило: если факт стоил времени (агент искал причину, писал что-то своё, поднимал
сервисы) — в тот же ход работы он фиксируется здесь или в `docs/06-troubleshooting.md`.
Знание, оставшееся только в переписке, теряется со следующей сессией.

Правило: если факт означает **отсутствие инструмента** — сначала заводится инструмент
(скилл, скрипт в `scripts`, правило), и только потом продолжается задача.
Заплатка, написанная внутри задачи, — это та же дыра, только замаскированная.

---

## 1. Артефакт-первым

Задача просит артефакт (Gherkin-сценарий, XML, описание, отчёт) — результат это
**артефакт**. Всё остальное (поднять живой слой, опубликовать базу, пройти прогон,
написать вспомогательный скрипт) делается только если входит в `<цель>` задачи.

Запрещено в ходе задачи, которая просит артефакт:

- разворачивать публикацию (Apache, `default.vrd`, веб-сервер) «на будущее»;
- решать попутно инфраструктурные проблемы базы (настройка OData, права, роли);
- писать свои скрипты «чтобы сэкономить» — инструмент либо уже есть в
  `scripts`/`.cline/skills`, либо это дыра, которую надо закрыть **до** задачи.

Признак подмены приоритета: прошло больше двух шагов, а артефакта всё ещё нет.

## 2. Предпосылки проверяются до работы (шаг 0)

До первого шага задачи проверить, выполнима ли она в принципе. Не проверено —
это и есть та дыра, из-за которой час уходит на тупик.

| Задача | Что проверить заранее | Если не выполнено |
|--------|----------------------|-------------------|
| Gherkin/Vanessa: **прогон** сценария | есть ли в базе Vanessa Automation (обработки по маскам `ванесс`, `vanessa`) | прогон невозможен; сценарий сдаётся как валидированный по реестру, а установка Vanessa — отдельная задача (`vanessa-project-bootstrap`) |
| Запись/изменение данных через `1c-toolkit` | снята ли защита записи в форме обработки (см. п.3) | запись невозможна; сказать сразу, не подбирать формулировки кода |
| «Поднять OData» / получить метаданные | заполнена ли `Константа.ПользовательСтандартногоИнтерфейсаOData` (см. п.4) | публикация даёт 200, но `$metadata` вернёт 404 |
| Задача по конкретной базе | есть ли база в `.v8-project.json`, поднят ли сервер на 6003 | `check-harness.ps1`, `start-harness.ps1` |

## 3. Защита записи в `1c-toolkit`

**Симптом.** `execute_code` возвращает:
`Операция запрещена: код содержит опасные ключевые слова: <слово>`
(например, при любом `Записать`).

**Факты.**

- Защита стоит в самой обработке `MCP_Toolkit.epf` и действует на чтение/запись.
- Параметр автозапуска `auto_allow_write` в `params.json` её **не снимает**
  (проверено: передано `true`, фильтр остался включён).
- Штатный путь один: снять флаг в **форме обработки** (SKILL.md скилла
  `1c-mcp-toolkit`, раздел про тесты на запись).

**Что делать в задаче.** Назвать это ограничение в преамбуле и в отчёте
(«Не проверено: запись невозможна, защита не снята»). Не подбирать обходные
формулировки BSL и не просить пользователя «скинуть флаг» вопросом на середине
работы — про ограничение сообщается один раз, в отчёте.

## 4. OData: публикация ≠ опубликованные метаданные

**Симптом.** Корень публикации (`http://localhost:8081/<база>`) отвечает 200,
а `/odata/standard.odata/$metadata` — 404.

**Причина.** В конфигурациях на БСП (КА2, ERP) стандартный интерфейс OData
включается настройкой **в базе**: `Обработка.НастройкаСтандартногоИнтерфейсаOData`
заполняет `Константа.ПользовательСтандартногоИнтерфейсаOData`. Пустая константа —
пустой состав публикуемых объектов.

**Факт.** Разворот публикации закрыт готовым инструментом
`scripts\publish-odata.ps1` (Apache + `default.vrd` с
`enableStandardOdata="true"`). Повторно его писать не нужно.
Настройка самого интерфейса OData — отдельная задача **записи** в базу, значит
упирается в п.3.

## 5. Реестр шагов Vanessa — единственный источник формулировок

- Шаги берутся из `.cline\skills\1c-vanessa-steps` (`scripts\search_steps.py`,
  `data\steps-library.json`), проверяются `scripts\validate.py`.
- В реестре **нет** шагов про HTTP/OData (поиск «OData» — 0 совпадений). Часть
  сценария про OData выражается шагом
  `И я выполняю код встроенного языка на сервере` + блок `"""bsl`.
  Сочинять шаг вида «И я проверяю ответ OData» — запрещено.
- Формат `.feature`: UTF-8 **без BOM**, CRLF, табы, первая строка `# encoding: utf-8`.

## 6. Перенос харнесса в единый репозиторий (сессия 2026-10-12)

**6.1. Массовая замена путей в скриптах не заменяет прогон скрипта.** Ключ замены
`(Split-Path -Parent (Split-Path -Parent $scriptDir))` не совпал с фактическим
текстом строки `$Root = Split-Path -Parent (Split-Path -Parent $scriptDir)`
(в строке только одна закрывающая скобка), поэтому корень в семи скриптах остался
на уровень выше репозитория. Ошибка не видна при чтении - её вскрыл только запуск
`install-vendor-skills.ps1` в новом каталоге. Правило: перенёс скрипт - запусти его
и посмотри лог, а не сверяй глазами.

**6.2. Вендорские репозитории не коммитятся.** `skills-vendor/` - 15 023 файла,
75 МБ (из них 7842 `.xml` - тестовые фикстуры cc-1c-skills, C++ исходники и `.epf`
в 1c-mcp-toolkit). В git они не хранятся: разворачиваются
`scripts\install-vendor-repos.ps1`, скиллы собираются `install-vendor-skills.ps1`.
Признак ошибки: `git add` вендоров не укладывается в 30 с и оставляет
`.git\index.lock`.

**6.3. Лимит команды 30 с.** Тяжёлые операции (`git add` десятков тысяч файлов,
robocopy больших каталогов) дробить по частям. Убитый по таймауту `git add`
оставляет `.git\index.lock`; если процессов `git` нет - удалить lock и повторить.

**6.4. Windows PowerShell 5.1.** Нет тернарного оператора `? :` (это PS 7).
Разбор `git status --porcelain`: `$_.Substring(0,2)` показывает ` M` (в рабочем
дереве) и `M ` (в индексе) неразличимо после `Format-Table` - печатать код
в квадратных скобках, иначе «469 изменённых» легко принять за чужую индексацию.

**6.5. Числа в документации проверяются по факту.** В `README.md`,
`docs\01-architecture.md` и `.clinerules\10-mcp-and-skills.md` стояло
«207 скиллов»; фактически на диске 206 (207 копирований, один конфликт имён
`composing-1c-queries` перекрыт). Считать - `(Get-ChildItem .cline\skills -Directory).Count`,
а не повторять цифру из прошлой версии текста.

## 7. Переменная `CLINE_MCP_SETTINGS_PATH` - одна на машину (сессия 2026-10-12)

**Симптом.** `check-harness.ps1` печатает
`[FAIL] CLINE_MCP_SETTINGS_PATH указывает в другое место: <чужой проект>\...`.

**Факт.** Переменная пользовательская и однозначная: in-project конфиг MCP активен ровно
у одного проекта за раз, у остальных серверов нет. Значение живёт только в реестре
(`HKCU:\Environment`), в файлах репозитория его нет (проверено поиском: `yarbp` по
репозиторию - 0 совпадений). Лечение: `scripts\enable-mcp.ps1` в нужном харнессе плюс
полный перезапуск VS Code. Читать значение сразу после записи нужно из реестра
(`Get-ItemProperty HKCU:\Environment`): `SetEnvironmentVariable` и чтение в одном пакете
команд дают старое значение.

**Вторая грабля рядом: серверов три, а папок в `.cline\mcp\` две.** Так и должно быть до
первой установки: `1c-platform-help` - это не бинарник, а Python-venv, его папка
`bsl-platform-help-context` появляется только после `install-mcp.ps1`. Признак
непоставленного сервера - `[FAIL] 1c-platform-help / mcp-bsl-context.exe - нет файла`.
Сборка venv идет минуты; запущенная фоном сборка умирает вместе с прерванной командой
родителя, после такого прерывания `.venv` остаётся недособранным (нет
`Scripts\mcp-bsl-context.exe`) и нужен повторный запуск `install-mcp.ps1`.
