# Грабли и уроки харнесса

Файл действует всегда. Сюда дописывается знание, добытое **по ходу работы**.

Правило: если факт стоил времени (агент искал причину, писал что-то своё, поднимал
сервисы) — в тот же ход работы он фиксируется здесь или в `docs/06-troubleshooting.md`.
Знание, оставшееся только в переписке, теряется со следующей сессией.

Правило: если факт означает **отсутствие инструмента** — сначала заводится инструмент
(скилл, скрипт в `scripts`, правило), и только потом продолжается задача.
Заплатка, написанная внутри задачи, — это та же дыра, только замаскированная.

---

## 1. Артефакт-первым

Задача просит артефакт (Gherkin-сценарий, XML, описание, отчёт) — результат это
**артефакт**. Всё остальное (поднять живой слой, опубликовать базу, пройти прогон,
написать вспомогательный скрипт) делается только если входит в `<цель>` задачи.

Запрещено в ходе задачи, которая просит артефакт:

- разворачивать публикацию (Apache, `default.vrd`, веб-сервер) «на будущее»;
- решать попутно инфраструктурные проблемы базы (настройка OData, права, роли);
- писать свои скрипты «чтобы сэкономить» — инструмент либо уже есть в
  `scripts`/`.cline/skills`, либо это дыра, которую надо закрыть **до** задачи.

Признак подмены приоритета: прошло больше двух шагов, а артефакта всё ещё нет.

## 2. Предпосылки проверяются до работы (шаг 0)

До первого шага задачи проверить, выполнима ли она в принципе. Не проверено —
это и есть та дыра, из-за которой час уходит на тупик.

## 3. Защита записи в `1c-toolkit`

**Симптом.** `execute_code` возвращает:
`Операция запрещена: код содержит опасные ключевые слова: <слово>`
(например, при любом `Записать`).

**Факты.**

- Защита стоит в самой обработке `MCP_Toolkit.epf` и действует на чтение/запись.
- Параметр автозапуска `auto_allow_write` в `params.json` её **не снимает**
  (проверено: передано `true`, фильтр остался включён).
- Штатный путь один: снять флаг в **форме обработки** (SKILL.md скилла
  `1c-mcp-toolkit`, раздел про тесты на запись).

**Что делать в задаче.** Назвать это ограничение в преамбуле и в отчёте
(«Не проверено: запись невозможна, защита не снята»). Не подбирать обходные
формулировки BSL и не просить пользователя «скинуть флаг» вопросом на середине
работы — про ограничение сообщается один раз, в отчёте.

## 4. OData: публикация ≠ опубликованные метаданные

**Симптом.** Корень публикации (`http://localhost:8081/<база>`) отвечает 200,
а `/odata/standard.odata/$metadata` — 404.

**Причина.** В конфигурациях на БСП (КА2, ERP) стандартный интерфейс OData
включается настройкой **в базе**: `Обработка.НастройкаСтандартногоИнтерфейсаOData`
заполняет `Константа.ПользовательСтандартногоИнтерфейсаOData`. Пустая константа —
пустой состав публикуемых объектов.

**Факт.** Разворот публикации закрыт готовым инструментом
`scripts\publish-odata.ps1` (Apache + `default.vrd` с
`enableStandardOdata="true"`). Повторно его писать не нужно.
Настройка самого интерфейса OData — отдельная задача **записи** в базу, значит
упирается в п.3.

## 5. Реестр шагов Vanessa — единственный источник формулировок

- Шаги берутся из `.cline\skills\1c-vanessa-steps` (`scripts\search_steps.py`,
  `data\steps-library.json`), проверяются `scripts\validate.py`.
- В реестре **нет** шагов про HTTP/OData (поиск «OData» — 0 совпадений). Часть
  сценария про OData выражается шагом
  `И я выполняю код встроенного языка на сервере` + блок `"""bsl`.
  Сочинять шаг вида «И я проверяю ответ OData» — запрещено.
- В реестре нет отдельного шага «вывести печатную форму»: печать выражается общими
  UI-шагами (`И я нажимаю на кнопку "..."` — открытие меню «Печать» и выбор пункта).
- Формат `.feature`: UTF-8 **без BOM**, CRLF, табы, первая строка `# encoding: utf-8`.

## 6. Перенос харнесса в единый репозиторий (сессия 2026-10-12)

**6.1. Массовая замена путей в скриптах не заменяет прогон скрипта.** Ключ замены
`(Split-Path -Parent (Split-Path -Parent $scriptDir))` не совпал с фактическим
текстом строки `$Root = Split-Path -Parent (Split-Path -Parent $scriptDir)`
(в строке только одна закрывающая скобка), поэтому корень в семи скриптах остался
на уровень выше репозитория. Ошибка не видна при чтении - её вскрыл только запуск
`install-vendor-skills.ps1` в новом каталоге. Правило: перенёс скрипт - запусти его
и посмотри лог, а не сверяй глазами.

**6.2. Вендорские репозитории не коммитятся.** `skills-vendor/` - 15 023 файла,
75 МБ (из них 7842 `.xml` - тестовые фикстуры cc-1c-skills, C++ исходники и `.epf`
в 1c-mcp-toolkit). В git они не хранятся: разворачиваются
`scripts\install-vendor-repos.ps1`, скиллы собираются `install-vendor-skills.ps1`.
Признак ошибки: `git add` вендоров не укладывается в 30 с и оставляет
`.git\index.lock`.

**6.3. Лимит команды 30 с.** Тяжёлые операции (`git add` десятков тысяч файлов,
robocopy больших каталогов) дробить по частям. Убитый по таймауту `git add`
оставляет `.git\index.lock`; если процессов `git` нет - удалить lock и повторить.

**6.4. Windows PowerShell 5.1.** Нет тернарного оператора `? :` (это PS 7).
Разбор `git status --porcelain`: `$_.Substring(0,2)` показывает ` M` (в рабочем
дереве) и `M ` (в индексе) неразличимо после `Format-Table` - печатать код
в квадратных скобках, иначе «469 изменённых» легко принять за чужую индексацию.

**6.5. Числа в документации проверяются по факту.** В `README.md`,
`docs\01-architecture.md` и `.clinerules\10-mcp-and-skills.md` стояло
«207 скиллов»; фактически на диске 206 (207 копирований, один конфликт имён
`composing-1c-queries` перекрыт). Считать - `(Get-ChildItem .cline\skills -Directory).Count`,
а не повторять цифру из прошлой версии текста. С 2026-10-12 числа, названные в доках,
сверяет `scripts\check-docs.ps1` (против карты источников `install-vendor-skills.ps1`);
повторы - §14.

## 7. Переменная `CLINE_MCP_SETTINGS_PATH` - одна на машину (сессия 2026-10-12)

**Симптом.** `check-harness.ps1` печатает
`[FAIL] CLINE_MCP_SETTINGS_PATH указывает в другое место: <чужой проект>\...`.

**Факт.** Переменная пользовательская и однозначная: in-project конфиг MCP активен ровно
у одного проекта за раз, у остальных серверов нет. Значение живёт только в реестре
(`HKCU:\Environment`), в файлах репозитория его нет (проверено поиском: `yarbp` по
репозиторию - 0 совпадений). Лечение: `scripts\enable-mcp.ps1` в нужном харнессе плюс
полный перезапуск VS Code. Читать значение сразу после записи нужно из реестра
(`Get-ItemProperty HKCU:\Environment`): `SetEnvironmentVariable` и чтение в одном пакете
команд дают старое значение.

**Вторая грабля рядом: серверов три, а папок в `.cline\mcp\` две.** Так и должно быть до
первой установки: `1c-platform-help` - это не бинарник, а Python-venv, его папка
`bsl-platform-help-context` появляется только после `install-mcp.ps1`. Признак
непоставленного сервера - `[FAIL] 1c-platform-help / mcp-bsl-context.exe - нет файла`.
Сборка venv идет минуты; запущенная фоном сборка умирает вместе с прерванной командой
родителя, после такого прерывания `.venv` остаётся недособранным (нет
`Scripts\mcp-bsl-context.exe`) и нужен повторный запуск `install-mcp.ps1`.

**6.6. `git push` в PowerShell 5.1 - ложный сбой.** git пишет прогресс push в stderr
(`To https://github.com/...`, `Everything up-to-date`), PowerShell 5.1 превращает это
в `NativeCommandError`, и харнесс видит код возврата 1 - хотя push уже прошёл. Гасить
шум: `git push --quiet origin main` (тихий push stderr не пишет). Проверять отправку по
факту, а не по коду возврата: `git ls-remote origin refs/heads/main` и сверить хеш с
`git rev-parse HEAD` либо `git status -sb` (нет ahead/behind - все отправлено).

**Второй источник того же ложного сбоя: переименование репозитория на GitHub.**
Старый адрес начинает отдавать редирект (`remote: This repository moved. Please use
the new location: ...`), после чего одна отправка может пройти, а следующая упасть:
`remote: fatal error in commit_refs` / `! [remote rejected] main -> main (failure)`.
Причина - не права и не ветка, а устаревший URL в `origin`. Лечение:
`git remote set-url origin <новый адрес>` и повторный push. Заодно сверять адрес в
`README.md`: после переноса он стоял в двух видах (старый на строке «Репозиторий:»,
новый в команде `git clone`).

## 8. Навигационные ссылки 1С: `ref` из UUID вручную не собирается (сессия 2026-10-12)

**Симптом.** `get_object_by_link` по ссылке
`e1cib/data/Документ.РеализацияТоваровУслуг?ref=<UUID без дефисов>` возвращает
`Объект не найден или недостаточно прав доступа`, хотя объект в базе есть.

**Причина.** Порядок байт в `ref` навигационной ссылки НЕ равен простому удалению
дефисов из `УникальныйИдентификатор`. UUID `b7b0ec60-1707-11f1-8429-df6a37009081`
в ссылке выглядит как `8429df6a3700908111f11707b7b0ec60`.

**Что делать.** Ссылку не собирать руками, а получать инструментом
`get_link_of_object` (object_description из результата `execute_query`) и брать
готовую строку оттуда. В Gherkin-сценарий подставлять именно её.

## 9. Печатные формы в БСП-конфигурации (КА2): состав не виден статикой

**Факт.** В КА2 печатные формы документа регистрируются кодом модуля менеджера
(процедура `Печать`), а не объектами метаданных: `get_metadata` по
`Документ.РеализацияТоваровУслуг` показывает только макеты `ПФ_MXL_*`, а состав
пунктов меню «Печать» там не виден. Перечислить печатные формы можно только вызовом
`Документы.<Имя>.Печать(...)` с коллекцией
`УправлениеПечатьюКлиент.НоваяКоллекцияПечатныхФорм()`, а этот метод - клиентский
(TF): серверный `execute_code` его не видит, а клиентский контекст обработки
`MCP_Toolkit.epf` не видит глобальный `Документы`. Значит, проверить состав печатных
форм через текущий toolkit нельзя - подпись пункта меню берётся из записи рекордера
или интроспекции формы, а не из метаданных.

## 12. Vanessa живёт внешней обработкой, а не «установкой в базу» (сессия 2026-10-12)

**Что выяснено про источник.** Vanessa Automation - [Pr-Mex/vanessa-automation](https://github.com/Pr-Mex/vanessa-automation),
BSD-3-Clause, релиз 1.2.043.1. Ставится **внешней обработкой**: релизный архив
`vanessa-automation-single.<версия>.zip` -> один `vanessa-automation-single.epf`
(библиотека шагов внутри). В конфигурации базы не появляется ни одного объекта,
поэтому высказывание «в базе нет Vanessa Automation» - неверная причина отказа
прогона. Рабочая строка запуска (подтверждена исходником `tools\onescript\run-behavior-check-session.os`):

```
1cv8c.exe ENTERPRISE /F"<база>" /N"<польз>" /P"<пароль>" /Execute "<...>\vanessa-automation-single.epf" /C"StartFeaturePlayer;VAParams=<...>\VAParams.json" /TESTMANAGER
```

Ключ `VAParams` (устаревшие имена `VBParams`, `КлиентыТестирования`,
`ДанныеКлиентовТестирования` тоже работают), регистр значения `/C` значения не
имеет. Полный набор ключей `VAParams.json` - `docs\JsonParams\JsonParamsRU.md` в
архиве с исходниками; готовые примеры - `tools\JSON\VBParams*.json`.
Результаты прогона: `.vanessa\status.txt` (0/1), `va-log.txt`, `junit\junit.xml`
(именно `junit.xml` - проверено прогоном; `Steps.xml` из статей не создаётся).
Инструменты харнесса: `scripts\install-vanessa.ps1`, `scripts\vanessa-run.ps1`
(кладут все артефакты в `.vanessa\`, каталог в `.gitignore`).

**Главная грабля - лицензия.** Vanessa поднимает в базе **два** клиентских сеанса
(менеджер тестирования + клиент тестирования), и платформа на этой машине второй
клиент **той же базы** отвергает:

```
Превышено ограничение лицензии для разработчиков на количество клиентов информационной базы.
Запуск приложения Тонкий клиент запрещен.
```

Проверено живыми запусками: два клиента базы `DemoSSL` (у неё сеансов не было)
поднимаются одновременно, а второй клиент `demo-ar` - отказ, пока в ней живёт
сеанс `1C MCP Toolkit` (он тоже клиент базы). Значит, перед прогоном Vanessa базу
надо освободить от **всех** клиентских сеансов, включая сервер toolkit (порт 6003).
Ошибка лицензии пишется в файл `/Out` и возвращает код 1, а до этого платформа
успевает проверить аутентификацию: без `/N`/`/P` сообщение будет
`Пользователь ИБ не идентифицирован` - это разные отказы, путать их нельзя.
Лицензии на машине: единственный `C:\ProgramData\<...>\1C\licenses\*.lic`
(программная, без HASP - служба `hasplms` остановлена).

**Порядок проверки перед прогоном (шаг 0):** 1) развёрнута ли обработка в
`.vanessa\`; 2) свободна ли база (нет клиентских сеансов, включая toolkit);
3) есть ли `user`/`password` в записи базы `.v8-project.json`.

## 11. `.v8-project.json` в PowerShell 5.1 читать с `-Encoding UTF8`

**Симптом.** `Get-Content .v8-project.json -Raw | ConvertFrom-Json` даёт путь вида
`...\OneDrive\Р”РѕРєСѓРјРµРЅС‚С‹\1C\...`, и `Test-Path -LiteralPath` по нему
возвращает `False` - база «не найдена», хотя она есть.

**Причина.** В PS 5.1 у `Get-Content` кодировка по умолчанию ANSI; UTF-8 файл
с кириллицей читается как кракозябры, и путь становится нерабочим.

**Что делать.** Читать конфиг так:
`Get-Content .v8-project.json -Raw -Encoding UTF8 | ConvertFrom-Json`.

## 15. Выгрузка конфигурации в каталог проекта: чем запускать и куда класть (сессия 2026-10-12)

**Задача.** Выгрузить XML конфигурации `КомплекснаяАвтоматизация` (база `demo-ar`,

```
--- Вывод платформы ---
Ошибка исключительной блокировки информационной базы.
```

**Факт 3. Конфигуратор выгружает параллельно с клиентским сеансом.** Тот же скилл с

свободной базы (он не занимает клиентскую лицензию).

**Факт 4. Раскладка.** Выгрузки живут в `dump\` (каталог уже прописан в `.gitignore`),

## 16. Выгрузка внутри корня тормозит офлайн-чекер: исключение - до входа в каталог (сессия 2026-10-14)

**Симптом.** `scripts\check-docs.ps1` перестал укладываться в 30-секундный лимит команды
агента: три прогона подряд оборвались по таймауту, каждый раз на шаге «Пути и файлы,
названные в доках». Фоновый прогон дошёл до конца между 70-й и 95-й секундой и вернул
код 0 - то есть расхождений не находил, но пользоваться им было нельзя.

**Причина.** Каталог `dump\` лежит внутри корня харнесса (§15): 127 378 файлов,
118 468 каталогов, 14,7 ГБ. Индекс имён файлов проекта строился
`Get-ChildItem $Root -Recurse -File -Force`, а `dump`, `.git`, `cache`, `logs`, `temp`,
`.code-index` исключались **внутри цикла** - после полного перечисления дерева, да ещё
проверкой `-like "*\$s\*"` по каждому из 127 тыс. элементов (около 760 тыс. сравнений строк).

**Замеры.** Листинг дерева `dump\` (robocopy `/L`) - 20 с на 127 378 имён;
`check-docs.ps1` целиком - 70-95 с.

**Что сделано.** Обход заменён собственным стеком по
`[IO.Directory]::EnumerateDirectories/EnumerateFiles`: каталог из `skipDirs` пропускается
**целиком, без входа**. После правки `check-docs.ps1` - 4,4 с, код 0, строка
«Доки сходятся с фактом».

**Правило.** Исключать каталог надо до входа в него. `Get-ChildItem -Recurse` с фильтром
в теле цикла - это не исключение, а полный обход дерева; по коду разницы не видно,
а на 127 тыс. файлов секундная проверка превращается в полутораминутную.

## 18. Автозапуск MCP toolkit и автоматический прогон Vanessa (сессия 2026-10-14)

**Что сделано.** Живой слой больше не требует действий человека:

- `scripts\start-toolkit.ps1` - поднимает встроенный сервер toolkit в базе из
  `.v8-project.json` (id/alias/name, по умолчанию `default`); `scripts\stop-toolkit.ps1` -
  гасит сеанс; `scripts\start-harness.ps1` вызывает первый, если порт 6003 молчит;
- `scripts\vanessa-run.ps1` - разворачивает обработку Vanessa сам и освобождает базу
  ключом `-FreeToolkit` (гасит сеанс toolkit до прогона и поднимает после).

**Механизм автозапуска обработки.** Проверено живой базой `demo-ssl`. Документированный
способ - параметр запуска `/C "startup;mode=embedded;port=6003"` (README_FULL.md вендора,
раздел «Автоматический запуск обработки из командной строки»):

```
1cv8c.exe ENTERPRISE /F"<база>" /N"<польз>" /P"<пароль>" /Execute "<...>\MCP_Toolkit.epf" /C"startup;mode=embedded;port=6003" /DisableStartupDialogs /DisableStartupMessages
```

Сервер отвечает `{"status":"healthy","mode":"native","port":6003}` через 9-12 с после
старта клиента. Второй механизм (`/C "autostart;<timestamp>;<params.json>"` - nonce и
signal-файлы, описан в `.cline\skills\1c-mcp-toolkit\scripts\start-1c.ps1`) требует
сохранённых настроек формы и временных файлов, поэтому в харнессе не используется.

**Закрытие сеанса toolkit.** Проверено: `POST http://127.0.0.1:6003/api/close_1c_session`
с телом `{}` возвращает 200 и освобождает порт - обработка закрывает свой сеанс 1С сама.
Резервный путь (ключ `-Force`) - остановка процесса 1С, в командной строке которого есть
`MCP_Toolkit.epf`: процесс находится через `Get-CimInstance Win32_Process`, гасится,
порт освобождается.

**Грабля PowerShell 5.1: у скалярного объекта нет `.Count`.** `Get-CimInstance` отдаёт
один объект, если совпадение одно, а результат функции идёт через конвейер и
разворачивается в скаляр. Тогда `"…: " + $sessions.Count` печатает пустое место вместо
числа. Проверено: у массива `@(...)` значение 1, у скаляра - `$null`. Правило: функцию,
возвращающую массив, оборачивать у вызывающего - `@(Get-ToolkitSessions)`.

**Грабля агента: правка и проверка в одной пачке команд идут параллельно.** Команды
массива `run_commands` выполняются одновременно, поэтому холостой прогон скрипта успел
прочитать файл до того, как `fix-encoding.ps1` дописал BOM: PowerShell 5.1 разобрал UTF-8
как ANSI и выдал каскад `Missing closing ')'` на кириллице. Правило: `.ps1` после правки
сначала прогнать через `fix-encoding.ps1`, а проверять **отдельной** командой.

**Прогон Vanessa - по требованию задачи.** Обязательной проверкой харнесса он не является:
запускается тогда, когда в цели задачи есть проверка сценарием (`.clinerules/30-verification.md`).
`check-harness.ps1` только сообщает состояние слоя и ничего не требует.

**Грабля `check-docs.ps1` и уборки артефактов.** Чекер требует, чтобы каждое имя файла,
названное в доках, существовало на диске. `status.txt` и `va-log.txt` создаются только
прогоном, поэтому после уборки `.vanessa\` строка README о результатах прогона стала
давать `[FAIL] не найден файл, названный в доке`. Лечится не созданием пустышек, а штатной
меткой той же строки: `<!-- check-docs:ignore: <причина> -->` (правило - `check-docs.ps1`, п.28).

## 19. Задача по базе, когда статический слой молчит (сессия 2026-10-14)

**`bsl-indexer serve` и демон индекса - разные процессы.** `serve` (его поднимает Cline по
stdio) читает индекс сам, но инструменты данных (`bsl_sql`, `grep_*`, `search_*`)
спрашивают демон по `http://127.0.0.1:8015`: без демона ответ - `daemon_offline`, а по
пути выгрузки - `not_started`. `get_stats` и `health` при этом отвечают, потому что читают
`.code-index\index.db` напрямую, - по ним «индекс работает» не проверяется. Поднимать:
`scripts\start-harness.ps1` или `bsl-indexer.exe daemon run` с `CODE_INDEX_HOME`. После
старта демон сверяет время и размер файлов: в этой сессии `main` (124 954 файла) - 307 с,
а путь выгрузки КА ждал очереди (`свободных мест 1`) и только потом ушёл в
`initial_indexing`. Первый шаг при молчащем индексе - `daemon status`, а не обход.

**Инструментов `1c-toolkit` в сеансе может не быть.** Сервер подключён по
`streamableHttp`; если он поднят **после** старта VS Code, Cline инструменты не
регистрирует. Перезапуск VS Code не обязателен: у обработки есть документированный REST
API (`skills-vendor\1c-mcp-toolkit\README_FULL.md`, раздел «REST API»,
`POST http://127.0.0.1:6003/api/<имя инструмента>`) - `/api/execute_code`,
`/api/execute_query`, `/api/get_object_by_link`, `/api/get_metadata`. Тело собирать
`ConvertTo-Json` и отдавать как UTF-8, ответ читать тоже как UTF-8
(`RawContentStream`) - иначе кириллица приходит кракозябрами.

**Тяжёлая база поднимает toolkit минутами.** `demo-ar` (КА, 4,3 ГБ, свободной RAM < 1 ГБ)
дала `/health` через ~3,5 мин после запуска клиента; `demo-ssl` - через 9-12 с. Ключ
`-NoWait` возвращает управление сразу, поэтому health надо опрашивать циклом, а не
считать, что сервер не поднялся.

**PS 5.1: `-EncodedCommand` на этой машине блокируется антивирусом** (`Этот сценарий
содержит вредоносное содержимое и был заблокирован`). Разовый сценарий оформлять файлом
в `temp` и запускать `-File`, а `.ps1` с кириллицей прогонять через
`scripts\fix-encoding.ps1` (UTF-8 без BOM ломает разбор). Отдельно: `$home` в PS 5.1 -
постоянная переменная (`VariableNotWritable`), для локальной брать другое имя.

**BSL: строки только в двойных кавычках.** Одиночные - литерал даты, поэтому
`СтрНайти(Реквизит.Имя, 'Адрес')` падает с `Неправильная константа типа Дата`.

**Печатные формы проверяются серверно (уточнение §9).** Для УПД точка входа -
`Обработки.ПечатьОбщихФорм.СформироватьПечатнуюФормуУПД(СтруктураТипов, ОбъектыПечати,
ПараметрыПечати)`, где `СтруктураТипов` - `Соответствие` вида
`"Документ.РеализацияТоваровУслуг" -> Массив`, а `ОбъектыПечати` - **`СписокЗначений`**
(`УправлениеПечатью.ЗадатьОбластьПечатиДокумента` вызывает `НайтиПоЗначению`; на
`Структуре` и `Соответствии` падает). Данные готовит
`РеализацияТоваровУслугЛокализация.ПолучитьДанныеДляПечатнойФормыУПД(ПараметрыПечати,
МассивОбъектов)`. Обе экспортные и серверные - их можно вызвать живьём и прочитать
фактический текст ячеек.

**Доменный факт (КА 2.5).** Строка УПД «Грузополучатель и его адрес» печатается
прочерком, когда в документе нет товаров (одни услуги): в
`Обработки.ПечатьОбщихФорм.ЗаполнитьРеквизитыШапкиУПД` стоит
`ЕстьГрузополучатель = Не ДанныеПечати.ТолькоУслуги`, а `ТолькоУслуги` - это «есть услуги
и нет товаров». Проверено живьём: документ из одной услуги - в ПФ `--`, документы с
товарами - «наименование грузополучателя, адрес».

## 20. Идемпотентный живой слой, дорогая `get_stats` и каталог `temp` (сессия 2026-10-14)

**Что сделано.**

- `scripts\start-toolkit.ps1` больше не плодит клиентские сеансы: сначала проверяется
  `/health`, затем - уже запущенный процесс 1С с `MCP_Toolkit` в командной строке
  (`Get-CimInstance Win32_Process`). Сеанс есть, а сервер молчит - второй клиент НЕ
  запускается, скрипт ждёт готовности этого. Повторный запуск - только ключом `-Force`
  (скрипт сам вызывает `scripts\stop-toolkit.ps1`).
- `scripts\stop-toolkit.ps1` научился гасить «зависший» сеанс: раньше он выходил сразу,
  если `/health` не отвечал, и такой сеанс убрать было нельзя, хотя порт и клиентскую
  лицензию он занимал. Теперь «гасить нечего» - только если и сервер молчит, и процессов
  с обработкой нет.
- `scripts\check-harness.ps1` печатает репозитории индекса (алиасы из `daemon.toml`) и их
  состояния (из `/health` демона), а при молчащем порте 6003 показывает PID уже
  запущенного сеанса toolkit; добавлен раздел «Временные файлы (temp)».
- Временные файлы задачи переехали из `.tmp` в `temp`: каталог в `.gitignore`, правило -
  `.clinerules/00-contract.md` (п.4) и `.clinerules/50-harness.md` (п.1).

**Замеры (эта машина, `CODE_INDEX_HOME=...\code-index-mcp\home`).**

| Вызов | Время |
|---|---|
| `stats` по корню проекта (124 954 файла, алиас `main`) | 9,0 с |
| `stats` по выгрузке КА (алиас `ka2`) | 6,6 с |
| `daemon status` (он же `GET /health` демона 8015) | 0,05 с |

`get_stats` без `repo` обходит все репозитории сразу, то есть платит оба этих счёта.
Ответ на вопрос «какие репо есть и живы ли они» дают `daemon.toml` и `/health` демона -
та же информация за 0,05 с. Правило занесено в `.clinerules/10-mcp-and-skills.md`
и `.clinerules/30-verification.md`.

**Грабли.**

1. `POST /stop` демона отвечает `{"stopping": true}` не мгновенно: процесс `daemon run`
   живёт ещё несколько секунд и держит свои лог-файлы (перенос падал с «файл занят другим
   процессом»). Ждать освобождения циклом, а не считать, что stop отработал. Побочный
   эффект остановки демона: при следующем запуске он сверяет время и размеры файлов заново
   (`main` - около 5 минут), поэтому останавливать его «на минутку» не стоит.
2. Процесс `bsl-indexer serve` (его поднимает Cline по stdio) - НЕ демон. Проверка
   «индексатор работает» по имени процесса врала: остановленный демон выглядел поднятым,
   пока жил `serve`. Признак - процесса с `daemon run` в командной строке
   (исправлено в `scripts\start-harness.ps1`).
3. CLI индексатора пишет прогресс в stderr, и PowerShell 5.1 превращает это в
   `NativeCommandError` - замеры и вызовы оформлять с `2>$null`; `$ErrorActionPreference`
   помогает не всегда, ошибку пишет сама оболочка.
4. У индексатора есть CLI-команды (`bsl-indexer.exe stats -p <путь>`, `query`), то есть
   объём индекса виден и без MCP. Правило то же: нужен редко и по конкретному репозиторию.

## 21. Форма электронного документа ЭДО строится из XML, а не из реквизитов (сессия 2026-10-14)

**Класс задачи.** Разбор расхождения между печатной формой и формой электронного документа
(кейс УПД): на печатной форме реквизит заполнен, а на форме ЭД строка пуста.

**Факт.** Это два разных источника данных, а не дефект показа. Печатная форма УПД собирается
кодом из реквизитов документа (`DataProcessors/ПечатьОбщихФорм/Ext/ManagerModule.bsl`,
процедура `ЗаполнитьРеквизитыШапкиУПД`). Форма электронного документа - результат
XSLT-преобразования XML файла сообщения (`ВизуализацияЭДОСлужебный.ВизуализацияДокумента` ->
`КонвертацияЭДО.ПреобразоватьФорматЭД`, правило берется из
`РегистрСведений.ПравилаПреобразованияФорматов`; текстов правил в конфигурации нет, они
загружаются из сервиса). Код 1С при показе XML не пересобирает: нет узла в XML - строка на
форме пуста.

**Следствие для диагноза.** Вопрос "почему на форме ЭД нет строки" решается двумя проверками:
есть ли узел в XML основного файла сообщения и не удален ли он при формировании. Для УПД
через ЕИС найден фильтр `ЭлектронноеАктированиеЕИС.ПроверитьГрузополучателей`: при совпадении
ИНН и КПП покупателя и грузополучателя (правило РДИК_0507) грузополучатель удаляется из
документа, а режим включается константой `ИспользоватьЭлектронноеАктированиеВЕИС`.

**Полный разбор** - `analysis\2026-10-14_1211_upd-gruzopoluchatel-edo.md` (цепочки процедур,
номера строк, чек-лист проверки в базе заказчика).

**Прием.** Очень крупные модули ЭДО (размером в мегабайты) обычным поиском по тексту не берутся:
адресовать сначала запрос к таблице функций индекса (`bsl_sql`), затем читать диапазон строк
через `read_file`.
