# Проверка результата

Правило: **нет проверки - нет результата**. Строка `Проверка:` в преамбуле должна
называть конкретное средство, а не намерение.

## Чем проверять (по слою)

| Что проверяем | Средство | Признак успеха |
|---------------|----------|----------------|
| Данные живой базы (запрос, документ, справочник) | MCP `1c-toolkit`, повторный `execute_query` | запрос возвращает ожидаемое значение |
| Изменение объекта в базе (запись, проведение) | MCP `1c-toolkit`: перечитать объект | поле содержит записанное значение; для документа - признак проведения |
| OData / HTTP-сервисы | HTTP-запрос к `http://127.0.0.1:6003/mcp` / к адресу базы | ответ содержит опубликованные метаданные |
| Структура и состав метаданных | MCP `1c-code-index`: `get_object_structure`, `get_object_profile` | объект найден, реквизиты совпадают |
| Синтаксис и объём BSL | скилл `1c-bsl-validate` | валидатор вернул OK |
| Качество кода, стандарты | скилл `1c-code-review` | замечаний нет либо они перечислены |
| XML объекта, формы, роли, СКД, расширения | скиллы `*-validate`, `1c-*-validate` | `Validation OK` / `валид` |
| Что платформа реально примет | загрузка в базу: `db-load-xml`, `db-update` | платформа не отвергла |
| Существование и сигнатура метода платформы | MCP `1c-platform-help`: `info` / `get_member` | метод есть, сигнатура совпала |
| Автотест (Gherkin/Vanessa), прогон | `scripts\vanessa-run.ps1` (Vanessa - внешняя обработка платформы) | `.vanessa\status.txt` = 0 и в `.vanessa\junit\junit.xml` `failures="0" errors="0"` |
| Gherkin/Vanessa, прогон невозможен (нет свободного клиентского слота в базе, `.clinerules/40-lessons.md` п.12) | скилл `1c-vanessa-steps`: `scripts\validate.py` | 0 невалидных шагов; в отчёте прямо сказано: «прогон не выполнен, причина - лицензия на клиентов / нет учётных данных» |

## Правила

1. **Обещанная проверка обязательна.** Назвал в преамбуле - выполнил. Если
   выполнить не удалось - сказать об этом прямо в отчёте.
2. **Повторное чтение после записи.** Любая запись в базу подтверждается
   повторным чтением через `1c-toolkit`, а не сообщением «документ проведён».
3. **Различать статику и живое.** OK валидатора по XML не означает, что объект
   создан в базе. Это разные утверждения и они не подменяют друг друга.
4. **Проверять саму выгрузку.** Если источник - индекс кода, сверять, что
   выгрузка отражает текущую конфигурацию базы (дата, ветка, наличие свежих
   изменений). Иначе вывод ограничивается: «по выгрузке на <дата>».
5. **Не пересказывать успех.** Отчёт содержит фактический вывод средства проверки
   (строку валидатора, результат запроса), а не его пересказ.
6. **Ограничения называть честно.** Если что-то не проверено - это указывается в
   отчёте отдельной строкой.

## Минимальный формат отчёта в конце задачи

```
Сделано: <что изменено/получено, с путями и именами>
Проверка: <средство, что именно вернуло>
Не проверено: <что осталось вне проверки и почему>
```
