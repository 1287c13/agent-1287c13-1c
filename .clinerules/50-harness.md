# Работа по самому харнессу (обязанности инженера харнесса)

Правило для второго класса задач - задач про инструмент агента, а не про базу 1С
(формат - `.clinerules/00-contract.md`, п.1.2). Слота базы в такой задаче нет.

## 1. Что можно и что нельзя менять

Можно:

- `START.md`, `AGENTS.md`, `README.md`, `SOURCES.md`;
- `.clinerules/*.md`;
- `docs/*.md`;
- `scripts/*.ps1`.

Нельзя (границы заданы устройством харнесса, а не вкусом):

- `.cline/skills/*` - каталог пересобирается целиком: `scripts/install-vendor-skills.ps1`
  первым делом делает `Remove-Item -Recurse`, правка потеряется на первом же запуске;
- `skills-vendor/*` - вендорские репозитории; правка потеряется при обновлении, а источник
  у них внешний (`SOURCES.md`);
- `.cline/mcp/*` - рантайм: бинарники и venv, ставятся `scripts/install-mcp.ps1`;
- `.vanessa/`, `dump/`, `logs/`, `cache/`, `.code-index/`, `temp/`, `analysis/` - рабочие каталоги (в `.gitignore`);
- `temp/` - единственное место временных файлов задачи: разовых скриптов, выгрузок ответов,
  логов, черновиков и сценариев `.feature`, собранных под задачу (`.feature` - в
  `temp\features\`, дефолт `scripts\vanessa-run.ps1`). Каталог создаётся при необходимости
  (`New-Item -ItemType Directory temp`), если его нет. Временный файл, оставленный в корне,
  `scripts\`, `docs\`, `.clinerules\` или `features\`, - нарушение протокола; каталог
  `features\` в корне - тоже (сценарии в git не хранятся, он закрыт `.gitignore`); наличие
  `temp\`, остатки `features\` и возраст сценариев в `temp\features\` проверяет
  `scripts\check-harness.ps1` (раздел «Прогон Gherkin/Vanessa»);
- `analysis/` - результаты анализа агента: разборы кейсов, расследования, объяснения
  «почему так». Имя файла - `<ГГГГ-ММ-ДД>_<ЧЧММ>_<краткое-имя>.md`; создаёт
  `scripts\new-analysis.ps1` (`-Name`, `-Title`, `-Task`). Каталог в `.gitignore`: анализ -
  рабочий артефакт, в репозиторий он не идет. В `docs\` уходит только правило или
  инструкция, выросшая из разбора;
- `scripts\set-cline-mcp-path.ps1` - команда "измени переменную": наводит
  `CLINE_MCP_SETTINGS_PATH` на конфиг MCP текущего каталога, ничего не проверяя и не
  поднимая (health и слои - отдельные действия);
- базы 1С (`databases[].path` из `.v8-project.json`) - только по явной задаче про базу;
- `.clinerules/40-lessons.md` - его дописывают и в задачах по базе (`.clinerules/00-contract.md`, п.4),
  поэтому это единственный файл правил, который меняется в обоих классах задач. В нём держат
  инварианты: разросшийся разбор переносят файлом в `analysis\`. Бюджет всегда-инжектируемого
  текста проверяет `scripts/check-context.ps1`; свой скилл добавляется источником в
  `scripts/install-vendor-skills.ps1` (порядок - `docs/05-skills.md`), иначе он исчезнет при
  первой же пересборке `.cline/skills`.

## 2. Обязанности, которые можно проверить

| Что найдено | Куда это уходит |
|---|---|
| Грабля из списка предпосылок (`.clinerules/40-lessons.md`, п.2) | новая проверка в `scripts/check-harness.ps1` |
| Дыра в инструментарии (нет средства для операции) | скрипт в `scripts/` или скилл, а не заплатка внутри задачи |
| Число, путь или утверждение в доке | правило в `scripts/check-docs.ps1`, если проверяемо офлайн |
| Новое знание, добытое дорого | строка в `.clinerules/40-lessons.md` тем же ответом |
| Разросся всегда-инжектируемый текст (правила, `AGENTS.md`, `40-lessons.md`) | разбор - файлом в `analysis\`, в правилах - инвариант; бюджет проверяет `scripts/check-context.ps1` |
| Расхождение, непроверяемое офлайн | строка «не проверено» в отчёте, без выдачи за проверенное |

Правило: дыра закрывается инструментом **до** следующей задачи, а не обходом в её ходе.

## 3. Проверка задачи по харнессу

Обязательный минимум:

1. `scripts/check-harness.ps1` - код возврата 0 (либо перечисленные и объяснённые замечания);
2. `scripts/check-docs.ps1` - код возврата 0: доки сходятся с локальным фактом;
3. если правка изменила счётный факт (число файлов правил, число скиллов, перечень путей) -
   обновлены **все** места, где этот факт назван; остальные ловит `check-docs.ps1`;
4. git: задача не закончена, пока правки не на GitHub. Порядок: `git status -sb`;
   `git add` только измененных файлов проекта; `git commit -m "..."`;
   `git push --quiet origin main`; сверить `git ls-remote origin refs/heads/main` с
   `git rev-parse HEAD`. Код возврата `git push` в PowerShell 5.1 - не показатель
   (`.clinerules/40-lessons.md`, п.6.6). Незакоммиченных правок в `START.md`, `AGENTS.md`,
   `README.md`, `SOURCES.md`, `.clinerules\`, `docs\`, `scripts\` не остается: каждая
   задача по харнессу заканчивается коммитом и отправкой. В git не идут артефакты
   `analysis\` и `temp\` - они закрыты `.gitignore`.

Оба чекера read-only: ничего не чинят и прав не требуют. Починка - отдельная задача.

## 4. Границы

- чекеры не заменяют живую проверку: факт о базе берётся из MCP-инструмента, а не из скрипта;
- `check-docs.ps1` сверяет доки с локальным фактом; появление новых версий у вендоров он
  не проверяет (это решение человека, а не расхождение);
- счётные факты считаются по карте источников (`scripts/install-vendor-skills.ps1`, `$sources`),
  а не рекурсивным обходом `SKILL.md`: у части вендоров каталоги дублированы
  (`.agents/skills` и `.claude/skills`), рекурсивный счёт даёт завышенное число;
- вендорские правила (`skills-vendor/*/rules/*.mdc`) не подключаются как постоянные
  (Cline не понимает `globs`/`alwaysApply`) и читаются по одному под задачу.

## 5. Результат анализа: `analysis\`

Задача, в которой агент что-то **разбирал** (почему расходится печатная форма и форма
электронного документа, откуда берутся остатки, что вызывает ошибку), заканчивается
файлом в `analysis\`, например
`analysis\2026-10-14_1211_upd-gruzopoluchatel-edo.md`.

- имя = метка времени (`ГГГГ-ММ-ДД_ЧЧММ`) плюс краткое имя анализа: время даёт
  уникальность, имя читается человеком;
- файл заводит `scripts\new-analysis.ps1 -Name <краткое-имя> [-Title ...] [-Task ...]`
  (он же создаёт каталог, если того нет);
- каталог закрыт `.gitignore`: разбор - рабочий артефакт агента, в репозиторий он не идет;
- путь файла называется в отчёте, в строке «Сделано»;
- в `docs\` уходит только то, что должно жить в репозитории: правило, инструкция,
  чек-лист, выросшие из разбора. Сам разбор в доки не копируется.

Правило то же, что и у временных файлов: артефакт, оставленный в переписке, теряется
со следующей сессией - следующий агент его не найдет.
