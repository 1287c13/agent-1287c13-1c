# Контракт 1C-агента (действует всегда)

## 1. Формат постановки задачи

Пользователь ставит задачу только в одном формате:

```
как <роль> сделай <действие> в базе <база> чтобы <цель> по START.md
```

| Слот | Что это | Как разбирать |
|------|---------|---------------|
| `<роль>` | область ответственности | задаёт набор скиллов и глубину проверки |
| `<действие>` | что нужно сделать | ядро задачи |
| `<база>` | информационная база | имя / алиас / путь; разрешается через `.v8-project.json` |
| `<цель>` | критерий готовности | по нему строится «Проверка» |
| `по START.md` | маркер протокола | обязательно прочитать `START.md` в корне проекта |

Если задача пришла НЕ в этом формате — не начинать работу, а попросить переформулировать.

## 2. Порядок работы

0. **Проверить предпосылки** (`.clinerules/40-lessons.md`, п.2): выполнима ли задача
   в этой базе вообще — есть ли Vanessa для прогона, снята ли защита записи, настроен
   ли OData. Невыполнимое называется сразу, а не после часа работы.
1. Прочитать `START.md` в корне проекта.
2. Разобрать слоты задачи. Разрешить `<базу>` через `.v8-project.json`.
3. Прочитать профильный скилл-роутер (см. `.clinerules/10-mcp-and-skills.md`).
4. Собрать и напечатать преамбулу (см. п.3).
5. Выполнить работу, используя MCP и скиллы. Приоритет — то, что просили в
   `<действие>`: артефакт задачи сначала, инфраструктура — только если входит в `<цель>`.
6. Проверить результат так, как обещано в «Проверка». Если проверка не проходит — не выдавать результат за готовый.

## 3. Обязательная преамбула

Первым блоком ответа — ровно четыре строки:

```
Слой: <какой слой решения задействован: MCP базы / индекс кода / справка платформы / скиллы / файлы проекта>
MCP: <какие MCP-серверы и инструменты будут вызваны; если MCP не нужен — «не требуется»>
Скиллы: <какие скиллы читаются; если не нужны — «не требуется»>
Проверка: <чем подтвердится результат: вывод MCP-инструмента / валидатор скилла / повторный запрос>
```

## 4. Жёсткие запреты

- **Не выдумывать.** Имена объектов метаданных, реквизитов, форм, полей, таблиц и методов платформы подтверждаются MCP-инструментом, скиллом или файлом проекта. «Помню, что в ЗУП есть реквизит X» — не подтверждение.
- **Не выдумывать MCP-методы.** Вызывать только инструменты, перечисленные в `.clinerules/10-mcp-and-skills.md` или полученные от самого сервера. Придуманный инструмент — ошибка.
- **Не писать свои скрипты вместо готового инструмента.** Если для операции есть MCP-инструмент или скилл — используется он. Bash/PowerShell/Python «с нуля» — только когда инструмента нет, и с явным указанием этого в преамбуле.
- **Не трогать файлы вне каталога проекта.** Информационные базы 1С (`*.v8-project.json` → `databases[].path`) — трогать только в рамках явно поставленной задачи.
- **Не заявлять об успехе без проверки.** Формулировки «должно работать», «вероятно» — не результат.

## 5. Границы возможностей

Разделение фиксировано и не размывается (детали — `docs/02-capabilities.md`):

- индекс кода и XML-выгрузка — статический анализ **без** запуска платформы;
- MCP-сервер базы — **живая** база (данные, выполнение кода, метаданные, OData);
- справка платформы — сигнатуры и типы API, стандарты BSL;
- скиллы — процедуры и форматы, не источники фактов о конкретной базе.

Факт о конкретной базе, полученный не из живого MCP-инструмента, а «по памяти», считается выдуманным.

## 6. Язык

Ответы, комментарии в коде и документация — по-русски. Идентификаторы метаданных — как в конфигурации.
