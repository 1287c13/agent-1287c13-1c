# Харнесс 1C-агента для Cline

Рабочее место, в котором пользователь ставит задачу в едином формате, а Cline
выполняет её как 1С-агент - на MCP-серверах и скиллах сторонних вендоров.

Этот репозиторий **и есть харнесс**: протокол работы агента, правила, скиллы,
конфиг MCP и скрипты установки. Кода 1С и баз данных в репозитории нет - харнесс
работает с ними снаружи. Единственное исключение - каталог `dump\`: в него кладутся
XML-выгрузки конфигураций, по подпапке на конфигурацию. Каталог закрыт `.gitignore`
и в git не попадает (шаг 9, раздел 5).
Репозиторий: **https://github.com/1287c13/agent-1287c13-1c.git**, ветка `main`. Клонировать харнесс на новую машину:

```powershell
git clone https://github.com/1287c13/agent-1287c13-1c.git C:\_works\1c-ai\agent
```

Дальше - установка с нуля ([раздел 2](#2-установка-с-нуля-по-шагам)).

## 0. Если вы видите это впервые

### Что перед вами

| Часть харнесса | Что это | Кто приводит в действие |
|----------------|---------|-------------------------|
| `START.md`, `AGENTS.md`, `.clinerules/` | протокол и постоянные правила агента | Cline читает их сам в начале каждой сессии |
| `.cline/skills/` | 206 скиллов из шести вендорских наборов | агент: `scripts/install-vendor-skills.ps1` |
| `.cline/cline_mcp_settings.json` | три MCP-сервера: `1c-toolkit` (живая база), `1c-code-index` (поиск по выгрузке), `1c-platform-help` (справка API платформы) | лежит в git, читается Cline |
| `.v8-project.json` | базы 1С и путь к платформе | заполнен, правится под себя |
| `scripts/*.ps1` | установка, запуск, диагностика | агент, по просьбе пользователя |

### Кто что делает

| Действие | Кто выполняет |
|----------|---------------|
| установка и переустановка MCP-серверов (`scripts/install-mcp.ps1`) | агент, по просьбе пользователя |
| вендорские репозитории и сборка скиллов (`install-vendor-repos.ps1`, `install-vendor-skills.ps1`) | агент, по просьбе пользователя |
| подключение MCP к Cline и переменная `CLINE_MCP_SETTINGS_PATH` (`enable-mcp.ps1`) | агент, по просьбе пользователя |
| диагностика и фон индексатора (`check-harness.ps1`, `start-harness.ps1`) | агент, по просьбе пользователя |
| открыть папку харнесса рабочей папкой VS Code (шаг 0) | человек |
| перезапустить VS Code после `enable-mcp.ps1` (шаг 6) | человек |
| поднять встроенный сервер живой базы (`scripts\start-toolkit.ps1`, шаг 7) | агент, по просьбе пользователя |
| сформулировать задачу в едином формате (раздел 4) | человек |

Скрипты из `scripts\` - это инструмент агента, а не задание для пользователя: агент
вызывает их сам, когда пользователь просит поставить или переустановить MCP, собрать
скиллы, проверить харнесс или поднять живой слой. Человеку остаются действия, требующие
GUI: открыть папку и перезапустить VS Code. Два действия ниже - ровно они.

Сносить `scripts\` не нужно: это единственный способ развернуть MCP, скиллы, индексатор и OData на новой машине или починить их после обновления вендора.

### Два действия, которые делает только человек

1. **Открыть папку харнесса рабочей папкой VS Code** (`File -> Open Folder...`).
   Cline ищет `AGENTS.md`, `.clinerules/`, `.cline/skills/`, `.v8-project.json`
   и `scripts/` **от корня рабочей папки**. Открыта другая папка - агент не
   увидит ни протокола, ни скиллов, ни баз и будет отвечать как обычный Cline.
2. **Попросить агента выполнить установку** ([раздел 2](#2-установка-с-нуля-по-шагам))
   и **полностью** перезапустить VS Code: переменная окружения читается только при старте.

Живой сервер 1С человек больше не поднимает: агент делает это сам - `scripts\start-toolkit.ps1`
открывает в базе проекта `.cline\mcp\1c-mcp-toolkit\MCP_Toolkit.epf` и включает встроенный
сервер. Скрипт идемпотентен: если сервер уже отвечает или сеанс 1С с обработкой запущен,
второй клиент не поднимается (повторный запуск - только с ключом `-Force`). Одна запущенная
обработка обслуживает одну базу, поэтому для задачи по другой базе агент гасит сеанс
(`scripts\stop-toolkit.ps1`) и поднимает его в нужной базе.

Проверка, что всё сделано: `scripts\check-harness.ps1`
([шаг 8](#шаг-8-проверка-установки)).

## 2. Установка с нуля, по шагам

Шаги выполняет **агент** по просьбе пользователя: достаточно попросить в чате поставить
или переустановить MCP, собрать скиллы, проверить харнесс. Руками пользователь делает
только то, что требует GUI: шаг 0 (открыть папку), шаг 6 (перезапустить VS Code),
шаг 7 (запустить сервер в 1С).

Что именно ставится и на каком шаге (три MCP-сервера, по одной папке на сервер,
подробная дока - в `mcp\`):

| MCP-сервер | Артефакт | Шаги установки | Как работает дальше |
|------------|----------|----------------|---------------------|
| `1c-toolkit` - живая база | `.cline\mcp\1c-mcp-toolkit\MCP_Toolkit.epf` | 2 (комплект вендора), 3 (копия в `.cline\mcp`) | вручную, в открытой 1С (шаг 7) |
| `1c-code-index` - структурный поиск по выгрузке | `.cline\mcp\code-index-mcp\bsl-indexer.exe` и `home\daemon.toml` | 3 (бинарник), 5 (конфиг демона), 9 (каталог выгрузки) | фоном: `start-harness.ps1` |
| `1c-platform-help` - справка API платформы | `.cline\mcp\bsl-platform-help-context\.venv\Scripts\mcp-bsl-context.exe` | 2 (исходники вендора), 3 (сборка venv) | сам Cline, при первом вызове инструмента |

Одна папка в `.cline\mcp\` - один MCP-сервер. Папок может быть **две, а не три**: сервер
справки `1c-platform-help` - это не бинарник, а Python-venv, который собирается шагом 3
из исходников вендора, поэтому до первой установки папки `bsl-platform-help-context` нет
вовсе. Признак непоставленного сервера - строка `[FAIL] 1c-platform-help / mcp-bsl-context.exe`
в выводе `scripts\check-harness.ps1`; лечение - повторный `scripts\install-mcp.ps1`
(сборка venv идет несколько минут).

Доки по серверам: `mcp\1c-mcp-toolkit\README.md`, `mcp\code-index-mcp\README.md`,
`mcp\bsl-platform-help-context\README.md`.

### Шаг 0. Открыть харнесс в VS Code

`File -> Open Folder...` -> папка харнесса. Признак правильной папки: в проводнике VS Code видны `.clinerules`, `START.md`, `scripts`. Если открыта другая папка, дальше работать не будет ничего.

### Шаг 1. Проверить пути в конфиге MCP

Файл `.cline\cline_mcp_settings.json` лежит в git и содержит **абсолютные пути**. Если харнесс лежит по тому же пути `C:\_works\1c-ai\agent`, править нечего. Если путь другой - замените в файле путь харнесса во всех местах, где он встречается:

- `command` у серверов `1c-platform-help` и `1c-code-index` - путь к `.exe` внутри `.cline\mcp\...`;
- `--config` и `CODE_INDEX_HOME` у `1c-code-index` - путь к `home\daemon.toml`;
- `-p` у `1c-platform-help` - каталог платформы 1С (например `C:\Program Files\1cv8\8.3.27.2130\bin`): он должен существовать и совпадать с `v8path` в `.v8-project.json`.

Образец с плейсхолдером вместо путей - `mcp\cline_mcp_settings.example.json`: подставьте свой путь вместо `<КОРЕНЬ>`. Правьте файл при **закрытом** VS Code - Cline тоже пишет в него (например, при включении и выключении сервера). После правки - полный перезапуск VS Code.

### Шаг 2. Вендорские репозитории

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File .\scripts\install-vendor-repos.ps1
```

Клонирует в `skills-vendor\` семь репозиториев вендоров: скиллы, правила `.mdc`, комплект `1C MCP Toolkit`, исходники сервера справки. Нужны git и интернет; это около 75 МБ и несколько минут. Скрипт идемпотентен: повторный запуск обновляет уже склонированные репозитории (`git pull`). В конце печатает коммиты - их фиксируют в `SOURCES.md` для воспроизводимости.

Если каталог уже существует, но внутри нет `.git` (набор принесён копированием), скрипт скажет об этом и предложит `-Force`: с этим ключом каталог переклонируется.

### Шаг 3. Бинарники MCP-серверов

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File .\scripts\install-mcp.ps1
```

Делает три вещи: качает `bsl-indexer.exe` (`1c-code-index`), кладёт комплект `MCP_Toolkit*.epf` (встроенный сервер живой базы) и собирает Python-venv сервера справки. Нужен интернет; сборка venv тянет `fastmcp`, `qdrant-client`, `grpcio` и идёт **несколько минут** - это нормально. Повторный запуск без `-Force` уже собранное не трогает.

Ключи: `-Force` (переустановить), `-PythonLauncher 'py -3.12'` (если venv не собирается на текущей версии Python), `-CodeIndexRelease <тег>` (взять не последний релиз индексатора).

### Шаг 4. Сборка скиллов

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File .\scripts\install-vendor-skills.ps1
```

Собирает `.cline\skills\` из `skills-vendor\*` - плоский каталог из 206 скиллов - и проверяет `name:` в frontmatter каждого `SKILL.md`. Каталог пересобирается целиком: правки, сделанные прямо в `.cline\skills\`, теряются.

### Шаг 5. Подключение MCP

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File .\scripts\enable-mcp.ps1
```

Три действия: создаёт `.cline\mcp\code-index-mcp\home\daemon.toml`, запускает фоновый индексатор и выставляет **пользовательскую переменную окружения** `CLINE_MCP_SETTINGS_PATH` на `.cline\cline_mcp_settings.json` внутри харнесса. Это единственное изменение вне каталога харнесса - без него Cline не читает in-project конфиг MCP.

Запускать после шага 3, иначе скрипт предупредит, что нет индексатора. Существующий `daemon.toml` не перезаписывается; свои каталоги индексации добавляются в него вручную (шаг 9).

### Шаг 6. Полностью перезапустить VS Code

Переменная окружения читается процессом при старте, поэтому закройте **все** окна VS Code и откройте заново. До перезапуска у агента не будет ни одного MCP-инструмента, даже если всё остальное готово.

### Шаг 7. Живая база: поднять встроенный сервер

Сервер поднимается автоматически, база берётся из `.v8-project.json` (поле `default`):

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File .\scripts\start-toolkit.ps1
```

Скрипт открывает `.cline\mcp\1c-mcp-toolkit\MCP_Toolkit.epf` в базе и включает встроенный сервер автозапуском обработки (`/C "startup;mode=embedded;port=6003"`), затем ждёт ответа `/health`. Проверка:

```powershell
Invoke-WebRequest http://127.0.0.1:6003/health -UseBasicParsing
# ожидаемо: {"status":"healthy","mode":"native","port":6003}
```

Одна запущенная обработка = одна база, и её сеанс занимает клиентскую лицензию базы. Для задачи по другой базе сеанс гасится (`scripts\stop-toolkit.ps1`) и поднимается в нужной базе - в самой задаче меняется только слот `<база>`. Ручной путь тоже остаётся: открыть `.epf` в 1С и нажать **«Запустить сервер»**.

### Шаг 8. Проверка установки

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File .\scripts\check-harness.ps1
```

Скрипт ничего не меняет: печатает `[ok]` / `[warn]` / `[FAIL]` по разделам «Конфигурация MCP», «Артефакты MCP-серверов», «Индексатор кода», «Живая база», «Проект 1С», «Скиллы». Код возврата 0 - замечаний нет, 1 - есть замечания, требующие действия.

Как читать результат:

| Строка в выводе | Что означает |
|-----------------|--------------|
| `[ok] CLINE_MCP_SETTINGS_PATH указывает на проект` | шаги 5 и 6 сделаны |
| `[FAIL] нет <корень>\.cline\cline_mcp_settings.json` | открыта не та рабочая папка (шаг 0) или файл удалён: он лежит в git, верните `git checkout -- .cline/cline_mcp_settings.json` |
| `[FAIL] CLINE_MCP_SETTINGS_PATH не задана` | не выполнен `enable-mcp.ps1` (шаг 5) |
| `[FAIL] ... указывает в другое место: <путь>` | переменная выставлена другим харнессом или старым проектом: выполните `enable-mcp.ps1` здесь и перезапустите VS Code |
| `[FAIL] 1c-code-index / bsl-indexer.exe - нет файла ...` | не выполнен `install-mcp.ps1` (шаг 3) |
| `[FAIL] 1c-platform-help / mcp-bsl-context.exe - нет файла ...` | не собрался venv сервера справки: повторите `install-mcp.ps1 -Force`, при необходимости с `-PythonLauncher` |
| `[FAIL] нет daemon.toml` | не выполнен `enable-mcp.ps1` (шаг 5) |
| `[FAIL] нет .v8-project.json в корне проекта` / `[FAIL] нет каталога платформы: <path>` | файла нет или `v8path` ведёт на несуществующий каталог: поправьте `.v8-project.json` |
| `[FAIL] индексатор не установлен - выполните install-mcp.ps1` | не выполнен шаг 3 |
| `[FAIL] скиллы не собраны` / `[FAIL] нет каталога .cline\skills` | не выполнен шаг 4; если скиллы собраны, а проверка их не видит - открыта не та рабочая папка (шаг 0) |
| `[warn] порт 6003 не отвечает` | не поднят сеанс toolkit: поднимите его - `scripts\start-toolkit.ps1` (шаг 7). Пока сеанса нет, задачи по живой базе недоступны, остальные работают |
| `[warn] индекс ещё не построен` | идёт первичная индексация или выгрузка лежит вне корня харнесса (шаг 9) |
| `[warn] нет shcntx_ru.hbk в v8path` | в каталоге платформы нет файла справки (в 8.3.25 его нет) - слой `1c-platform-help` молчит |
| `[warn] база <id>: путь не найден` | база 1С переехала: поправьте `path` в `.v8-project.json` |
| `Проблем не найдено.` | минимальная установка завершена |

Минимально рабочий харнесс - ни одного `[FAIL]`. Строки `[warn]` про порт 6003 и индекс допустимы: они означают, что не поднят соответствующий слой, а не что установка сломана.

### Шаг 9. Слой кода: выгрузки конфигураций (по желанию)

MCP-сервер `1c-code-index` работает **не по базе, а по выгрузке** XML (скилл `db-dump-xml`). Пока выгрузки нет, слой отвечает пусто, а задачи по структуре метаданных решаются только живой базой.

Выгрузки живут в `dump\` - **по подпапке на конфигурацию**, поэтому в каталоге их может
лежать несколько (`dump\КомплекснаяАвтоматизация`, `dump\<другая конфигурация>`, ...).
Каталог в `.gitignore`: свежий клон харнесса приходит без выгрузок, их надо сделать заново.

1. Выгрузить конфигурацию в свою подпапку (база и платформа берутся из `.v8-project.json`):

```powershell
# полная выгрузка; повторная - -Mode Changes (инкремент по ConfigDumpInfo.xml)
.\.cline\skills\db-dump-xml\scripts\db-dump-xml.ps1 `
  -InfoBasePath "C:\Users\art8k\OneDrive\Документы\1C\DemoARAutomation20" `
  -UserName "Администратор" `
  -ConfigDir "C:\_works\1c-ai\agent\dump\КомплекснаяАвтоматизация" -Mode Full
```

Движок скрипт выбирает по имени exe в `-V8Path`: каталог платформы - конфигуратор
(`1cv8.exe DESIGNER`), путь к `ibcmd.exe` - утилита `ibcmd`. **При занятой базе нужен
конфигуратор**: `ibcmd` требует базу без чужих сеансов и отвечает «Ошибка исключительной
блокировки информационной базы», если в ней работает клиент (например сервер 1C MCP Toolkit).
Выгрузка идёт десятки минут - её стоит запускать фоном, лог положить рядом с выгрузкой.

2. Прописать каталог индексатору в `.cline\mcp\code-index-mcp\home\daemon.toml` - своя секция на каждую выгрузку:

```toml
[[paths]]
path = "C:/_works/1c-ai/agent/dump/КомплекснаяАвтоматизация"
alias = "ka2"
language = "bsl"
```

`path` - каталог выгрузки (прямые слэши, кириллица допустима), `alias` - короткое имя для инструментов (`repo = "ka2"`), `language = "bsl"` - обязателен: без него сервер не отдаёт BSL-инструменты (`find_path_bsl`, `bsl_sql`, `search_terms` и остальные).

3. Перечитать конфиг: запустить `scripts\start-harness.ps1` (он печатает статус демона) или выполнить `bsl-indexer.exe daemon reload` с тем же `CODE_INDEX_HOME`. После правки `daemon.toml` переподключите сервер `1c-code-index` в панели MCP - Cline список инструментов сам не обновляет.
4. Индекс строится в `<выгрузка>\.code-index\index.db`. Индексировать каталог можно только после **конца** выгрузки: пока она идёт, дерево дописывается.

Правки в базе, не отражённые в выгрузке, для агента невидимы: он ответит «по выгрузке на <дата>».

Выгрузка конфигуратора содержит **только основную конфигурацию**: объекты подключённых
расширений в неё не попадают, и в индексе их кода не будет. Проверено на `demo-ar`:
172 общих модуля расширения `InfostartToolkitCORP` (префикс `ИТК`) в выгрузке
отсутствуют. Поэтому числа из живой базы и число папок выгрузки напрямую несравнимы -
расхождение считается по перечню имён объектов (`.clinerules/40-lessons.md`, п.15).

### Шаг 10. Прогон Gherkin-сценариев: Vanessa Automation внешней обработкой

Vanessa Automation (BDD для 1С) **не ставится в конфигурацию базы**: это внешняя обработка, которую платформа запускает ключом `/Execute`. В базе не появляется ни одного объекта метаданных - отдельного шага установки, как для MCP-серверов, здесь нет.

| Что | Значение |
|-----|----------|
| Проект | [Pr-Mex/vanessa-automation](https://github.com/Pr-Mex/vanessa-automation) (BSD-3-Clause, текущий релиз 1.2.043.1) |
| Поставка | релизный архив `vanessa-automation-single.<версия>.zip`, внутри один `vanessa-automation-single.epf` - в него уже упакована библиотека шагов |
| Релизы | [github.com/Pr-Mex/vanessa-automation/releases](https://github.com/Pr-Mex/vanessa-automation/releases) |
| Документация | [pr-mex.github.io/vanessa-automation/dev](https://pr-mex.github.io/vanessa-automation/dev/); полный список ключей `VAParams.json` - `docs/JsonParams/JsonParamsRU.md` (лежит в архиве с исходниками, ветка `develop`) |

1. Разворачивать обработку вручную не нужно: `scripts\vanessa-run.ps1` сам достаёт
   `.vanessa\vanessa-automation-single.epf` из самого свежего релизного архива
   `vanessa-automation-single*.zip` в Загрузках (каталог `.vanessa\` в git не хранится,
   как и все `*.epf`). Локальный вспомогательный скрипт развёртывания (в git не хранится)
   разложит обработку отдельно:

```powershell
# взять самый свежий vanessa-automation-single*.zip из Загрузок
powershell -NoProfile -ExecutionPolicy Bypass -File .\scripts\install-vanessa.ps1
# или указать архив явно
powershell -NoProfile -ExecutionPolicy Bypass -File .\scripts\install-vanessa.ps1 -Zip "$env:USERPROFILE\Downloads\vanessa-automation-single.1.2.043.1.zip" -Force
```

2. Прогнать сценарии:

```powershell
# весь каталог features
powershell -NoProfile -ExecutionPolicy Bypass -File .\scripts\vanessa-run.ps1

# один сценарий
powershell -NoProfile -ExecutionPolicy Bypass -File .\scripts\vanessa-run.ps1 -Features .\features\Smoke\ДымовойТест_ОткрытиеСпискаНоменклатуры.feature

# база занята сеансом toolkit - погасить его на время прогона и поднять обратно
powershell -NoProfile -ExecutionPolicy Bypass -File .\scripts\vanessa-run.ps1 -FreeToolkit

# не запускать, только собрать VAParams.json и напечатать строку запуска
powershell -NoProfile -ExecutionPolicy Bypass -File .\scripts\vanessa-run.ps1 -NoRun
```

Прогон делается **по требованию задачи**: обязательной проверкой харнесса он не является.
Агент запускает его, когда в цели задачи есть прогон сценария в базе (`.clinerules/30-verification.md`).

Скрипт берёт базу и платформу из `.v8-project.json`, собирает `.vanessa\VAParams.json` и поднимает сеанс менеджера тестирования:

```
1cv8c.exe ENTERPRISE /F"<путь к базе>" /N"<пользователь>" /P"<пароль>" /Execute ".vanessa\vanessa-automation-single.epf" /C"StartFeaturePlayer;VAParams=.vanessa\VAParams.json" /TESTMANAGER
```

Строка запуска и имена ключей `VAParams` не выдуманы, а взяты из самого проекта Vanessa: `tools\onescript\run-behavior-check-session.os` (функция `ПолучитьСтрокуЗапускаСборки`) и примеры `tools\JSON\VBParams*.json`. Работают и устаревшие имена (`VBParams` вместо `VAParams`, `КлиентыТестирования` вместо `ДанныеКлиентовТестирования`), порядок ключей в `/C` не важен.

Результаты прогона складываются в `.vanessa\`: `status.txt` (0 - сценарии прошли, 1 - есть упавшие), `va-log.txt` (лог по шагам; при падении шага - текст ошибки, выполняемый код и техданные), `junit\junit.xml` (машиночитаемый отчёт). Имя файла отчёта - именно `junit.xml` (проверено прогоном), а не `Steps.xml`, как иногда пишут в статьях. Без `-NoWait` скрипт ждёт закрытия сеанса (`-TimeoutSec`, по умолчанию 1800 с) - в этом харнессе команда оболочки живёт 30 с, поэтому длинные прогоны запускайте с `-NoWait` и смотрите статус отдельно. <!-- check-docs:ignore: status.txt и va-log.txt создаёт прогон в .vanessa\, в репозитории их нет по устройству -->

**Прогон проверен на этой машине дважды.** 12.10.2026 (Vanessa 1.2.043.1, платформа 8.3.27.2130): сценарий `features\Smoke\ДымовойТест_ВыполнениеКодаНаСервере.feature` прогнан в базе `demo-ssl` - `status.txt` = `0`, в `junit\junit.xml` `failures="0" errors="0" tests="1"`. 14.10.2026 тем же сценарием проверен автоматический путь: `-FreeToolkit` сам погасил сеанс toolkit, прогон прошёл (`tests="1" failures="0" errors="0"`, `time="26.805"`), сеанс тестирования закрылся сам. Сценарий намеренно не привязан к объектам метаданных, поэтому годится как дымовой для любой базы.

**Два ограничения машины, о которые спотыкается первый запуск.**

- **Лицензия.** Vanessa поднимает в базе два клиентских сеанса: менеджер тестирования и клиент тестирования. Платформа без клиентской лицензии нужного уровня отвечает на второй клиент той же базы: `Превышено ограничение лицензии для разработчиков на количество клиентов информационной базы`. Перед прогоном базу надо освободить - закрыть все её клиентские сеансы, включая встроенный сервер `1C MCP Toolkit` (он тоже клиент базы). Сеанс toolkit прогон гасит и возвращает сам с ключом `-FreeToolkit` (`scripts\stop-toolkit.ps1` / `scripts\start-toolkit.ps1`); чужие интерактивные окна 1С закрывает человек. Прогон идёт в обычном окне 1С: нужен интерактивный рабочий стол, не RDP-сессия без графики.
- **Учётные данные.** Если в базе есть пользователи, логин и пароль берутся из полей `user`/`password` записи базы в `.v8-project.json` (и подставляются и в сеанс менеджера, и в клиент тестирования). Без них платформа отвечает `Пользователь ИБ не идентифицирован`.

## 4. Как ставить задачу

Два формата. Основной - задача по базе 1С:

```
как <роль> сделай <действие> в базе <база> чтобы <цель> по START.md
```

- `<роль>` - на каком слое работать: `программист 1С` (индекс кода и скиллы сборки), `аналитик` (живая база и индекс), `тестировщик` (Gherkin/Vanessa и живая база), `администратор` (скиллы `db-*`, `web-*`). Роль задаёт приоритетный слой, а не набор скиллов: Cline держит активными все правила и выбирает скиллы по релевантности задачи;
- `<база>` - алиас, `id` или `name` записи из `.v8-project.json`, либо путь к базе целиком;
- `<цель>` - зачем; она же критерий проверки;
- `по START.md` - маркер протокола, обязателен: без него агент не обязан читать `START.md`.

Второй формат - задача по самому харнессу, без базы:

```
как инженер харнесса сделай <действие> чтобы <цель> по START.md
```

Так ставятся задачи про инструмент агента: правила `.clinerules/`, доки `docs/`, скрипты
`scripts/`, формат задачи. Границы - `.clinerules/50-harness.md`; проверка таких задач -
`check-harness.ps1` и `check-docs.ps1`.

### Базы этого харнесса

| `id` в `.v8-project.json` | База 1С | Что писать в `<база>` |
|---------------------------|---------|----------------------|
| `demo-ar` | DemoARAutomation20 (по умолчанию) | `demo`, `демо`, `DemoAR`, `DemoARAutomation20`, `автоматизация` |
| `demo-ssl` | DemoSSL | `ssl`, `бсп` |
| `demo-erp` | DemoERPUH | `erp`, `ерп` |
| `demo-trd` | DemoTrd | `trd`, `упп` |

Путь можно указать и целиком: `File="C:\...\DemoARAutomation20"`. При неоднозначности агент спрашивает, а не выбирает наугад.

### Первая задача: проверить, что протокол работает

Возьмите read-only задачу и посмотрите на форму ответа:

```
как аналитик сделай список документов с реквизитами в базе демо чтобы проверить связку с моделью по START.md
```

Признаки исправного харнесса: ответ начинается преамбулой `Слой / MCP / Скиллы / Проверка` с названными MCP-инструментами и заканчивается блоком `Сделано / Проверка / Не проверено`. Если агент отвечает без преамбулы - он не видит правила: вернитесь к шагу 0 (рабочая папка) и шагу 8 (диагностика).

Чего не стоит брать в первую задачу: запись в базу через `1c-toolkit` (при защите обработки любой код со словом `Записать` отклоняется), прогон Vanessa (Vanessa Automation ставится внешней обработкой и в конфигурацию базы не входит, но прогон требует освободить базу от других клиентских сеансов - см. шаг 10), задачи по 1С 7.7, Docker-валидацию, npm/JVM-инструменты - этого в харнессе нет (см. «чего харнесс не умеет» в [docs/06-troubleshooting.md](docs/06-troubleshooting.md)).

Примеры задач:

```
как программист 1С сделай обработку печати счёта в базе демо чтобы печаталось по кнопке по START.md
как тестировщик сделай Gherkin-тест проведения документа в базе File="C:\...\DemoARAutomation20" чтобы документ проводился с комментарием по START.md
как аналитик сделай описание структуры документа ПоступлениеТоваров в базе erp чтобы понять движения по регистрам по START.md
как аналитик сделай анализ способов ввода корректировочной счет-фактуры в базе автоматизация чтобы я мог ответить на вопрос пользователя по START.md
```

Последний пример - аналитическая задача по выгрузке: структуру и код агент берёт из
индекса кода над `dump\` (шаг 9), а текущее состояние данных - из живой базы. Если в
`dump\` лежит несколько конфигураций, в задаче достаточно назвать нужную базу - подпапку
и `alias` агент находит в `daemon.toml`.

## 6. Диагностика

```powershell
# полная проверка харнесса: что установлено, что запущено, чего не хватает
powershell -NoProfile -ExecutionPolicy Bypass -File .\scripts\check-harness.ps1

# не разошлись ли доки и правила с фактом: числа скиллов, имена файлов, имена MCP-инструментов
powershell -NoProfile -ExecutionPolicy Bypass -File .\scripts\check-docs.ps1

# посмотреть, куда указывает переменная Cline
[Environment]::GetEnvironmentVariable('CLINE_MCP_SETTINGS_PATH', 'User')
```

Оба скрипта ничего не меняют: первый отвечает на вопрос «жив ли харнесс», второй - «не
разъехались ли доки с содержимым каталога». Расхождения, найденные вторым, правятся
отдельной задачей: `как инженер харнесса ... по START.md`.

Частые случаи - [docs/06-troubleshooting.md](docs/06-troubleshooting.md).

Типовые причины:

- **агент отвечает как обычный Cline, без преамбулы** - рабочая папка VS Code не корень харнесса: не видны ни `.clinerules\`, ни `AGENTS.md`, ни `.v8-project.json` (шаг 0);
- **агент не видит MCP-серверы** - VS Code не перезапускали после `enable-mcp.ps1` либо переменная указывает в другое место: выполните `enable-mcp.ps1` в этом харнессе и закройте **все** окна VS Code;
- **`daemon_offline`** - не запущен индексатор, выполните `start-harness.ps1`;
- **`get_stats` отвечает, а инструменты данных молчат** - так и должно быть: `get_stats` читает индекс напрямую, данные спрашивают демон. Дорогой вызов для проверки живости не нужен: список репозиториев и статусы показывает `scripts\check-harness.ps1` (алиасы - из `daemon.toml`, статусы - из `/health` демона);
- **нет инструментов живой базы** - не поднят сеанс toolkit: `scripts\start-toolkit.ps1` (порт 6003, одна база за раз; гасится `scripts\stop-toolkit.ps1`);
- **сервер справки молчит** - в `v8path` нет файла `shcntx_ru.hbk` (в 8.3.25 его нет; используйте 8.3.27);
- **`execute_code` отвергает код** («код содержит опасные ключевые слова») - включена защита записи в `MCP_Toolkit.epf`, снимается флагом в форме обработки;
- **OData-публикация открывается, а `$metadata` даёт 404** - стандартный интерфейс OData в базе не настроен (пустая константа БСП), публикует `scripts\publish-odata.ps1`;
- **сценарий Vanessa написан, но не прогоняется** - обработку разворачивает сам `scripts\vanessa-run.ps1` (из релизного архива в Загрузках); если в базе занят клиентский сеанс (в том числе `1C MCP Toolkit`), запускайте прогон с ключом `-FreeToolkit` - он гасит сеанс toolkit и возвращает его обратно (шаг 10).

## 7. Что выходит за пределы харнесса

Единственное действие выходит за каталог харнесса: пользовательская переменная окружения `CLINE_MCP_SETTINGS_PATH`.
Cline читает MCP только из глобального файла; эта переменная указывает на файл
**внутри харнесса** (`.cline\cline_mcp_settings.json`). Обратного пути нет -
без переменной in-project MCP недостижим. Выставляет ее агент скриптом `enable-mcp.ps1` (по просьбе пользователя) либо пользователь вручную:

```powershell
[Environment]::SetEnvironmentVariable('CLINE_MCP_SETTINGS_PATH', 'C:\_works\1c-ai\agent\.cline\cline_mcp_settings.json', 'User')
# снять переменную
[Environment]::SetEnvironmentVariable('CLINE_MCP_SETTINGS_PATH', $null, 'User')
```

После ручного изменения - полный перезапуск VS Code. Проверять значение лучше через `GetEnvironmentVariable` (раздел 6): в уже запущенных окнах PowerShell значение в `$env:` остаётся старым.

Переменная **одна на пользователя**, поэтому in-project конфиг MCP активен ровно у одного проекта за раз: включив харнесс, вы выключаете MCP у соседнего проекта, пока он не выполнит `enable-mcp.ps1` у себя. Если `check-harness.ps1` печатает `[FAIL] CLINE_MCP_SETTINGS_PATH указывает в другое место: <путь>` - переменная осталась от другого проекта. В репозитории этот путь не хранится ни в одном файле: значение живёт только в переменной окружения пользователя (`HKCU:\Environment`).

Дополнительно, по желанию: ярлык в автозагрузке на `start-harness.ps1`.
