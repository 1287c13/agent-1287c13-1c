# Внешняя интеграция: очередь задач на сервере

Слой, через который задача попадает в харнесс не из чата Cline, а от внешней системы:
страницы задач в браузере или HTTP-клиента. Установка для человека - шаг 11
[README.md](../README.md); здесь - устройство слоя и контракт обмена.

## 1. Зачем слой

Формат задачи остаётся тем же (`.clinerules/00-contract.md`, п.1): слоты роль, действие,
база, цель превращаются в строку контракта. Меняется только доставка - задачу составляет
отправитель, а ответ читается из очереди, а не из чата. Отсюда требования к слою:

- **отправитель заполняет только слоты**: формулировку собирает `integration\task.py`,
  поэтому браузер и командная строка дают один и тот же текст задачи;
- **очередь одна и она на сервере**: у задачи один источник правды, а машина агента
  держит только рабочий каталог задачи на время работы;
- **стадии считает сервер**: `queued -> claimed -> delivered -> running -> done`,
  отправитель видит, где задача находится, а не только «принята»;
- **ответ - данные результата**: `GET /api/answer/<id>` отдаёт markdown агента или
  страницу HTML по нему.

## 3. Где живёт очередь

Очередь - каталог `server.root` из `deploy\config.json` (по умолчанию `queue\` в корне
харнесса; на хостинге это отдельный каталог вне кода). Каталог закрыт `.gitignore`.

| Путь | Что это |
|------|---------|
| `inbox\task_<id>.json` | задача ждёт агента |
| `processing\task_<id>.json` | агент взял задачу и ведёт её (со стадией и историей `progress`) |
| `archive\task_<id>.json` | задача завершена, файл оставлен для разбора |
| `outbox\result_<id>.json` | итог задачи - его читает страница и внешний клиент |
| `failed\rejected_<id>.json` | задача, отклонённая проверкой формы, с причиной |
| `agents\<имя>.json` | отметка живого агента: кто, когда, какую задачу ведёт |
| `events.jsonl` | журнал событий очереди: `task_created`, `claimed`, `progress`, `finished`, `reclaimed` |

На машине агента каталога очереди нет. Есть только `temp\queue\<id>\prompt.txt`
(формулировка для Cline) и `temp\queue\<id>\answer.md` (файл ответа). После записи
результата watcher удаляет `temp\queue\<id>\`.

## 4. Настройки

Один файл `deploy\config.json`; образец - `deploy\config.example.json`. В git он не
хранится: в нём ключи доступа.

```json
{
  "server": {
    "host": "127.0.0.1",
    "port": 8760,
    "public_url": "https://example.org/agent",
    "root": "queue",
    "cors_origin": "*",
    "max_body": 262144,
    "databases": ["ka2", "demo-ssl"],
    "clients": [
      { "name": "browser", "key": "ключ-браузера", "allow_harness": false },
      { "name": "agent-01", "key": "ключ-агента", "allow_harness": true }
    ]
  },
  "agent": {
    "name": "agent-01",
    "server_url": "https://example.org/agent",
    "key": "ключ-агента",
    "deliver": "uri",
    "interval": 2.0,
    "idle_interval": 15.0,
    "claim_ttl_s": 300
  }
}
```

- `server.root` - каталог очереди; относительный путь считается от корня харнесса;
- `server.databases` - перечисление баз для формы. Сервер сверяет с ним слот `<база>`
  (опечатка отправителя видна сразу), но **путь к базе знает только агент**: он
  разрешает слот по `.v8-project.json` на своей машине;
- `server.clients` - ключи доступа. Пустой список - сервер отвечает 503 на все
  защищённые маршруты: публиковать его «без ключей» нельзя;
- `allow_harness` - разрешение клиенту ставить задачи `mode=harness` (по инструменту
  агента). Браузеру по умолчанию запрещено: он ставит задачи по базе;
- `agent.deliver` - режим доставки по умолчанию (`uri`, `manual`, `echo`);
- `agent.claim_ttl_s` - сколько секунд задача закреплена за агентом без продления;

## 5. Ключи и доступ

Каждый клиент входит своим ключом. Ключ передаётся заголовком
`X-Integration-Token: <ключ>` либо `Authorization: Bearer <ключ>`. Отправитель задачи
определяется **по ключу**, а не по полю в теле: иначе клиент мог бы назваться чужим
именем, и журнал перестал бы отвечать на вопрос «кто это поставил».

| Маршрут | Ключ | Что делает |
|---------|------|-----------|
| `GET /api/health` | не нужен | состояние сервера и счётчики очереди (без путей и ключей) |
| `POST /api/auth` | не нужен | проверка ключа: имя клиента, `allow_harness`, список баз |
| `GET /` | не нужен | страница задач (`integration\web`) |
| остальные `GET`/`POST /api/*` | нужен | очередь, ответы, агенты |

Страница хранит ключ в `localStorage`: история ключей - `integration.keys`, активный -
`integration.activeKey`, адрес сервера - `integration.serverUrl`. Ключ лежит открытым
текстом, поэтому на странице есть предупреждение, удаление отдельного ключа и кнопка
«Забыть все ключи» с подтверждением. Это осознанный выбор: сервер не ставит cookie и
не заводит сеансов, которые нужно чистить на его стороне.

## 6. Стадии задачи

| Стадия | Кто ставит | Что означает |
|--------|-----------|--------------|
| `queued` | сервер | задача в inbox, ждёт агента |
| `claimed` | сервер при claim | агент взял задачу, claim закреплён на `claim_ttl_s` |
| `delivered` | watcher | задача передана в Cline (URI открыт, подтверждение записано) |
| `running` | watcher | Cline выполняет задачу; стадия продлевает claim |
| `done` | агент через `--write-result` | работа выполнена, ответ записан |
| `error` | watcher | сбой доставки: задача не выполнена |
| `failed` | сервер | попытки агента кончились (`claim` истёк `MAX_ATTEMPTS` раз) |
| `timeout` | сервер | результат не записан за `timeout_s` |

Переходы не откатываются: повторная стадия ниже текущей принимается как продление
claim, но историю не переписывает. `claim` истекает - задача возвращается в `queued`
(событие `reclaimed`); после третьей неудачи закрывается как `failed`.

Сервер отдаёт по задаче `wait_hint` (человеческая подсказка), `elapsed_s` и `progress` -
историю стадий с временем и пояснением. Браузер не вычисляет стадии сам.

## 7. HTTP-контракт

Постановка задачи (`POST /api/task`, ключ клиента):

```json
{ "role": "программист 1С", "action": "найди документы без склада",
  "goal": "список с причиной", "db": "ka2", "deliver": "auto", "timeout_s": 1800 }
```

Ответ `202`:

```json
{ "task_id": "t-20261019-111908-cfd4f8", "state": "queued",
  "prompt": "как программист 1С сделай найди документы без склада в базе ka2 чтобы список с причиной по START.md",
  "status_url": "/api/status/t-20261019-111908-cfd4f8" }
```

| Метод и путь | Назначение |
|--------------|------------|
| `POST /api/task` | поставить задачу; `400` - форма или база не приняты (причина в `errors`) |
| `GET /api/status/<id>` | стадия, подсказка, время, история стадий |
| `GET /api/status?ids=a,b` | состояния пачки задач (страница опрашивает свои) |
| `GET /api/history?limit=20` | последние задачи и счётчики |
| `GET /api/answer/<id>?format=md` | ответ задачи: markdown (`md`) или страница (`html`) |
| `GET /api/agents` | отметки агентов: кто жив, какую задачу ведёт |
| `GET /api/config` | список баз и публичный адрес (после входа) |
| `GET /api/events?limit=50` | последние события очереди |
| `POST /api/agent/claim` | агент берёт задачу: `{"agent": "...", "ttl_s": 300}` |
| `POST /api/agent/progress` | стадия: `{"id": "...", "stage": "delivered", "message": "..."}` |
| `POST /api/agent/result` | итог: `{"id": "...", "status": "done", "answer": "..."}` |
| `POST /api/agent/reclaim` | вернуть задачи с истёкшим claim, закрыть просроченные |

Проверка формы: пустое тело или не объект JSON - `400`, несоответствие схеме - `400`
с перечнем, слишком большое тело - `413` (предел `server.max_body`).

Пример из 1С или скрипта:

```
curl -H "X-Integration-Token: ключ-браузера" -H "Content-Type: application/json" ^
     -d "{\"action\":\"проверить остатки\",\"db\":\"ka2\"}" https://example.org/agent/api/task
```


## 8. Путь задачи

1. **Отправитель** (страница задач или HTTP-клиент) вызывает `POST /api/task`.
2. **Сервер** проверяет форму (`integration\task.py`): слоты, режим, база из
   `server.databases`, право клиента на `mode=harness`. Отклонённая задача уходит в
   `failed\rejected_<id>.json` с причиной. Принятая сразу кладётся в `inbox` - второго
   разборщика (журнала и его позиции) больше нет: очередь принадлежит серверу.
3. **Watcher** (`integration\watcher.py`) вызывает `POST /api/agent/claim`. Сервер
   переименовывает файл задачи из `inbox` в `processing` - из двух агентов задачу
   возьмёт ровно один - и выдаёт `claim` с TTL.
4. **Watcher** создаёт `temp\queue\<id>\`, пишет `prompt.txt` и `answer.md` (скелет),
   передаёт задачу в Cline и отмечает стадию `delivered`, затем `running`.
5. **Cline** выполняет формулировку, заполняет `answer.md` и вызывает
   `integration\agent.py --write-result --task <id> --file <answer.md>`. Команда
   отправляет `POST /api/agent/result`; сервер пишет `outbox\result_<id>.json`,
   переносит задачу в `archive` и закрывает её стадией `done`.
6. **Watcher** видит терминальную стадию, удаляет `temp\queue\<id>\` и берёт следующую
   задачу. Пока Cline работает, watcher ждёт и раз в 30 с отправляет `running`
   (продление claim).

Задача, закреплённая за агентом, который умер, возвращается в очередь по истечении
`claim_ttl_s` (событие `reclaimed`), а после `MAX_ATTEMPTS` попыток закрывается как
`failed`. Просроченные по `timeout_s` закрывает `POST /api/agent/reclaim`, который
watcher вызывает на простое раз в минуту.

## 9. Доставка в Cline (мост)

Мостик - обработчик URI расширения Cline: `vscode://saoudrizwan.claude-dev/task?prompt=<текст>`
создаёт новую задачу Cline, то есть человеку в чат писать не нужно. Длина URI ограничена
реестром Windows и командной строкой, поэтому в нём едет короткая ссылка на файл
`temp\queue\<id>\prompt.txt`, а не полный текст задачи.

| Режим (`agent.deliver`, ключ `--deliver`) | Что делает |
|-------------------------------------------|-----------|
| `uri` (по умолчанию) | открывает URI: задача создаётся в Cline автоматически |
| `manual` | ничего не открывает: печатает URI и строку запуска - их применяет человек |
| `echo` | Cline не трогает совсем: watcher сам записывает результат (проверка цепочки) |
| `auto` | режим канала; задача с `deliver` отличным от `auto` берёт свой режим |

После открытия ссылки доставка проверяется журналом сессий Cline
(`integration\transport\cline.py`): появилась сессия с идентификатором задачи -
доставка подтверждена. «Ссылка принята оболочкой» результатом не считается: обработчик
URI работает только при видимой панели Cline, поэтому попытка повторяется, а в итоге
watcher пишет стадию `error` и путь к файлу формулировки.

## 10. Как агент записывает ответ

Агент, выполнивший задачу, заполняет файл ответа (строки `Слой:`, `MCP:`, `Скиллы:`,
`Проверка:`, `Сделано:`, `Не проверено:` и текст ниже) и вызывает:

```
py -3 integration\agent.py --write-result --task t-20261019-111908-cfd4f8 --file temp\queue\t-20261019-111908-cfd4f8\answer.md
```

Команда разбирает файл, отправляет `POST /api/agent/result` и печатает итог. Тот же
результат виден в браузере: стадия `done`, кнопки «Скачать ответ (.md)» и «Открыть
ответ (HTML)».


## 11. Хостинг: Passenger и nginx

Корень приложения Passenger - каталог `integration\` (там лежит `passenger_wsgi.py`).
Слой не требует отдельных пакетов: только стандартная библиотека Python 3.

Директивы nginx (фрагмент, а не полный конфиг сайта: TLS, статика и остальные
location у каждого хостинга свои):

```nginx
location /agent/ {
    passenger_base_uri /agent;
    passenger_app_root /home/user/agent/integration;
    passenger_enabled on;
    passenger_python /home/user/venv/bin/python3;
    passenger_startup_timeout 60;
    client_max_body_size 256k;
}
```

Что важно знать:

- **базовый URI.** Сайт может быть опубликован по `/agent`. Passenger кладёт префикс в
  `SCRIPT_NAME`; `integration\passenger_wsgi.py` дополнительно берёт `PASSENGER_BASE_URI`,
  если `SCRIPT_NAME` пуст, и очищает `PATH_INFO` - иначе `/api/health` стал бы
  `/agent/api/health` и дал 404;
- **переменные окружения.** `INTEGRATION_ROOT` - корень харнесса, `INTEGRATION_CONFIG` -
  файл настроек. По умолчанию корень берётся из расположения `integration\`, а настройки -
  `deploy\config.json`;
- **каталог очереди.** `server.root` должен указывать на каталог, куда процессу Passenger
  разрешена запись; код приложения и очередь на хостинге лучше держать раздельно;
- **процессов может быть несколько.** Claim задачи - переименование файла, поэтому
  параллельные процессы не выдадут одну задачу дважды. `agents\` покажет, сколько
  агентов работает;
- **HTTPS.** Слой не терминирует TLS: сертификат и редирект с HTTP - задача nginx.
  Адрес в `server.public_url` и `agent.server_url` должен быть уже `https://`;
- **локальная проверка.** `deploy\run-server.bat` поднимает тот же WSGI-код на
  `wsgiref` - адрес и порт из `server.host`/`server.port`.

## 12. Что запрашивает браузер

Страница не опрашивает сервер на простое:

- при загрузке - один `POST /api/auth`, если сохранён ключ (проверка, что он ещё годен);
- при входе - `POST /api/auth` и один `GET /api/history`;
- при отправке задачи - `POST /api/task`, дальше опрос статуса **только этой задачи**;
- интервал опроса растёт 3 -> 5 -> 10 -> 20 -> 30 с и останавливается на терминальной
  стадии; на скрытой вкладке опрос замирает, после возврата - сразу один запрос;
- история и состояние сервера - только по нажатию кнопки.

Ни SSE, ни WebSocket: каждый открытый поток занимает процесс Passenger, а очередь
меняется редко и адресно.

## 13. Проверка слоя

```
py -3 integration\agent.py --health
py -3 integration\agent.py --list
py -3 integration\watcher.py --once --deliver echo
py -3 integration\transport\http_server.py --port 8760
powershell -NoProfile -ExecutionPolicy Bypass -File .\scripts\check-harness.ps1
```

`--health` показывает счётчики очереди и живых агентов, `--list` - последние задачи,
`--once --deliver echo` прогоняет цепочку «claim -> доставка -> результат» без Cline.

Ограничения, которые нужно называть вслух:

- режимы `uri` и `manual` работают на машине агента с Windows: `os.startfile` - часть
  платформы, на Linux доставка вернёт ошибку (для проверки есть `echo`);
- Cline ведёт одну задачу за раз, поэтому очередь последовательная;
- прогон под настоящим Passenger и HTTPS на машине разработки не проверялся: проверен
  WSGI-контракт (в том числе с базовым URI) и локальный сервер на `wsgiref`.

- `agent.idle_interval` - пауза watcher-а на пустой очереди (не чаще 15 с).
