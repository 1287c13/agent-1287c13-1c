# Внешняя интеграция: задача из очереди

Слой, через который задача попадает в харнесс не из чата Cline, а от внешней системы:
окна задач, HTTP-клиента или строки в общем журнале. Установка для человека - шаг 11
[README.md](../README.md); здесь - устройство слоя и контракт обмена.

## 1. Зачем слой

Формат задачи остаётся тем же (`.clinerules/00-contract.md`, п.1): слоты роль, действие,
база, цель превращаются в строку контракта. Меняется только доставка - задачу составляет
отправитель, а ответ читается из очереди, а не из чата. Отсюда требования к слою:

- **отправитель заполняет только слоты**: формулировку собирает `integration\task.py`,
  поэтому три отправителя (окно, HTTP, файл) дают один и тот же текст задачи;
- **проверка до очереди**: база, которой нет в `.v8-project.json`, - ошибка отправителя,
  задача до агента не доходит;
- **ответ - файл, а не сообщение**: результат попадает в `queue\outbox`, откуда его читает
  и окно задач, и внешний клиент.

| `deploy\config.example.json` | образец настроек; копия `deploy\config.json` в git не хранится |

## 3. Раскладка очереди (`queue\`, в git не хранится)

| Путь | Что это |
|------|---------|
| `queue\tasks.jsonl` | журнал задач: одна строка - одна задача; дописывают все отправители |
| `queue\.watch_offset` | позиция чтения журнала, её ведёт watcher |
| `queue\inbox` | задача, разложенная watcher-ом и ждущая агента |
| `queue\processing` | транзитное состояние: задача лежит здесь, пока агент её доставляет (упавший агент оставляет её тут) |
| `queue\archive` | задача, по которой записан хоть какой-то итог: уже при доставке (`delivered`), окончательный - после `--write-result` |
| `queue\outbox` | итог задачи в виде result - его читает окно и внешний клиент |
| `queue\answers` | файл ответа агента |
| `queue\prompts` | полная формулировка задачи: на неё ссылается URI доставки |
| `queue\failed` | непринятые строки журнала и задачи: причина должна быть видна отправителю |
| `queue\bridge.jsonl` | журнал доставки: режим, URI, пути, коды |
| `queue\.watcher.lock` | замок единственного экземпляра watcher-а; обновляется каждым проходом |
| `queue\watcher.pid` | pid-файл watcher-а, поднятого фоном (`scripts\start-watcher.ps1`) - им пользуются `scripts\stop-watcher.ps1` и проверки; снятия замка не заменяет |
| `queue\gui_state.json` | последние поля окна задач (роль, база, адрес сервера, отправленные задачи) |

Порядок чтения отметок о watcher-е: возраст берется из **свежей** из двух отметок - замок
`queue\.watcher.lock` (watcher обновляет его каждый проход) и позиция `queue\.watch_offset`
(пишется только при появлении новых строк). Поэтому на простое живой watcher виден по замку, а
не по позиции журнала; так его и видят `GET /api/health`, `scripts\check-harness.ps1` и окно задач.

Атомарность: любой JSON пишется во временный файл рядом и переименовывается `os.replace`,
поэтому читатель видит либо старый файл, либо новый целиком. Файлы с суффиксом `.tmp`
читатели игнорируют: недописанный результат никто не примет за готовый.

## 4. Контракт задачи

Обязательные поля: `id`, `created_at`, `source`, `mode`, `role`, `action`, `prompt`.
Необязательные: `goal` (при пустой цели поля в задаче нет, а формулировка обходится без
«чтобы <цель>»), `db` (нужен только для `mode=db`), `client`, `deliver`, `timeout_s`, `note`.
Полное описание - `integration\schemas\task_schema.json`.

| Поле | Значение |
|------|----------|
| `id` | идентификатор вида `t-<ГГГГММДД>-<ЧЧММСС>-<6 hex>`; присваивает отправитель |
| `created_at` | местное время, `ГГГГ-ММ-ДДTЧЧ:ММ:СС` |
| `source` | `gui`, `http`, `file`, `cli` - кто положил задачу в журнал |
| `client` | `<COMPUTERNAME>\<USERNAME>` отправителя |
| `mode` | `db` - задача по базе (слот базы обязателен), `harness` - задача по харнессу (базы нет) |
| `role` | роль из контракта: программист 1С, тестировщик, аналитик, администратор, инженер харнесса. Роль задает и вид задачи: «инженер харнесса» - `harness`, остальные - `db` (окно задач выводит режим из роли) |
| `action` | слот `<действие>`: что нужно сделать; формулировка - одна строка |
| `goal` | слот `<цель>` (не обязателен): критерий готовности; без него формулировка обходится без «чтобы <цель>» |
| `db` | id, алиас, name или путь из `.v8-project.json`; для `harness` - `null` |
| `prompt` | готовая строка контракта одной строкой |
| `deliver` | режим доставки для этой задачи: `uri`, `lg-task`, `manual`, `echo`, `auto` |
| `timeout_s` | порог застревания доставки, с; по умолчанию 1800 |
| `priority` | резерв: очередь разбирается строго по порядку поступления |
| `note` | пометка отправителя, на разбор задачи не влияет |

Строка журнала - та же задача одним JSON-объектом без переводов строк.

## 5. Контракт результата

Пишет `integration\agent.py`; обязательные поля - `task_id`, `status`, `written_at`, `answer`.
Полное описание - `integration\schemas\result_schema.json`.

| Поле | Значение |
|------|----------|
| `status` | `done`, `error`, `timeout`, `delivered` |
| `delivered` | задача передана в Cline, ответ ждёт записи (промежуточный статус) |
| `done` | работа выполнена и записана через `--write-result` |
| `error` | задача не выполнена |
| `timeout` | доставка не завершилась за `timeout_s`: задача застряла в `queue\processing` (упавший агент) |
| `layer`, `mcp`, `skills`, `verification` | строки преамбулы из файла ответа |
| `done`, `not_verified` | строки отчёта из файла ответа |
| `answer` | текст файла ответа целиком |
| `delivery` | каким режимом задача передана в Cline |
| `prompt_file`, `answer_file` | пути файлов формулировки и ответа |
| `started_at`, `delivered_at`, `written_at`, `duration_s` | отметки времени |

## 6. Путь задачи

1. **Отправитель** (окно, HTTP, ручная правка журнала) дописывает строку в `queue\tasks.jsonl`.
   Задача не кладётся в inbox сразу: единственный разборщик очереди - watcher.
2. **Watcher** читает журнал с сохранённой позиции (`queue\.watch_offset`), проверяет каждую
   строку по схеме и по `.v8-project.json`, принятые кладёт в `queue\inbox`, отклонённые -
   в `queue\failed` с причиной. Неполная последняя строка не берётся.
3. **Агент** (`--process`) берёт самую старую задачу из inbox, переносит её в
   `queue\processing`, создаёт файл ответа и передаёт задачу в Cline.
4. Итог доставки записывается сразу: результат `delivered` уезжает в `queue\outbox`,
   задача - в `queue\archive`. `processing` после этого пуст - оно транзитное.
5. **Cline** выполняет формулировку как обычную задачу протокола START.md, заполняет файл
   ответа и вызывает `--write-result`: тот же файл итога перезаписывается статусом `done`
   (поля доставки в нём сохраняются), задача уже лежит в `queue\archive`.
6. Задача, застрявшая в `processing` дольше `timeout_s`, помечается `--sweep` статусом
   `timeout`. Зависший итог `delivered` sweep не трогает: он уже в archive, и закрывается
   он записью ответа (раздел 11 `docs\06-troubleshooting.md`).

Watcher работает постоянно, а не «пока есть задачи»: он не завершается от ошибки отдельного
прохода (ошибка уходит в `logs\watcher.log` и в `queue\bridge.jsonl` событием `watcher_error`)
и не выходит сам на пустой очереди. Поднимают его фоном - `scripts\start-watcher.ps1`, гасят
явно - `scripts\stop-watcher.ps1`; второй экземпляр отвергается замком `queue\.watcher.lock`,
а потеря замка останавливает лишний процесс. Признак жизни - возраст замка (см. раздел 3).

## 7. Доставка в Cline (мост)

Мостик - обработчик URI расширения Cline: `vscode://saoudrizwan.claude-dev/task?prompt=<текст>`
создаёт новую задачу Cline, то есть человеку в чат писать не нужно. Длина URI ограничена
реестром Windows и командной строкой, поэтому в нём едет короткая ссылка на файл
`queue\prompts\prompt_<id>.txt`, а не полный текст задачи.

| Режим (`--deliver`) | Что делает |
|---------------------|-----------|
| `uri` (по умолчанию) | открывает URI: задача создаётся в Cline автоматически |
| `lg-task` | то же плюс POST в вебхук Cline, если задан адрес (ключ `watcher.webhook_url` в настройках) |
| `manual` | ничего не открывает: печатает URI и строку запуска - их применяет человек |
| `echo` | Cline не трогает совсем: только файлы и журналы (проверка цепочки) |
| `auto` | режим канала; задача с `deliver` отличным от `auto` берёт свой режим |

Результат доставки (режим, статус, URI, пути файлов, строка запуска, пояснение) попадает в
`queue\bridge.jsonl` и в итоговый result.

Ограничения моста: `os.startfile` есть только в Windows, на другой платформе режимы `uri` и
`lg-task` возвращают ошибку доставки; Cline ведёт одну задачу за раз, поэтому очередь строго
последовательная и следующий шаг начинается после записи результата.

## 8. Как агент записывает ответ

Файл ответа создаёт `--prepare` (агент делает это и сам, взяв задачу): строки `Слой:`, `MCP:`,
`Скиллы:`, `Проверка:`, `Сделано:`, `Не проверено:`, ниже - свободный текст ответа.

```
py -3 integration\agent.py --prepare --task <id>
py -3 integration\agent.py --write-result --task <id> --file "queue\answers\answer_<id>.md"
```

`--write-result` разбирает файл, собирает результат по схеме и кладёт его в outbox. В чате
отправителю ответ не виден: читается только очередь. Статус итога задаётся ключом
`--status done|error`, короткое пояснение - `--message`.

## 9. HTTP-интерфейс

| Метод и маршрут | Что делает | Ответ |
|-----------------|-----------|-------|
| `GET /api/health` | состояние очереди: счётчики, позиция журнала, жив ли watcher | 200 |
| `POST /api/task` | принимает задачу по схеме, дописывает строку в журнал | 202 либо 400 с перечнем ошибок |
| `GET /api/result/<id>` | результат задачи | 200 с результатом либо 404 с состоянием задачи |
| `GET /api/tasks?limit=N` | последние результаты и счётчики | 200 |

Задача не попадает в inbox сразу: разбор очереди держит один watcher, поэтому сервер только
дописывает журнал и отвечает 202. Коды: пустое тело или необъект JSON - 400, несоответствие
схеме - 400, тело больше предела (256 КБ) - 413, неизвестный маршрут - 404, исключение в
обработчике - 500 с причиной (оборванного соединения без ответа не бывает).

Запуск локально (по умолчанию слушает только localhost):

```
deploy\run-server.bat
curl http://127.0.0.1:8760/api/health
```

Хостинг: приложение `application(environ, start_response)` из `integration\transport\wsgi.py`;
Passenger поднимает его через `integration\transport\passenger_wsgi.py`. Корень харнесса
задаётся переменной `INTEGRATION_ROOT` (по умолчанию - каталог выше `integration\`).

**Токен.** Если он задан (ключ `server.token` в настройках или переменная `INTEGRATION_TOKEN`),
любой маршрут требует заголовок `X-Integration-Token` либо параметр `token`; иначе - 401.
На публичном хостинге токен обязателен: открытый `POST /api/task` пускает чужой текст прямо
в задачу агента.

## 10. Окно задач

`gui\AgentGUI.py` (Tkinter, запуск - `deploy\run-gui.bat`): заполняются слоты - роль, что нужно
сделать, база из `.v8-project.json`, цель (не обязательно). Режим задачи окно не спрашивает:
он выводится из роли - «инженер харнесса» это задача по харнессу (база не нужна), любая другая
роль - задача по базе (база обязательна). Ролей и баз может быть много: список баз целиком
берется из `.v8-project.json`.

Слева форма задачи, справа таблица последних задач с состоянием и блок ответа. Очередь
опрашивается раз в две секунды; строка состояния показывает размер журнала, счётчики
inbox/processing/outbox/failed, время обновления и жив ли watcher (или отвечает ли сервер).
Поля формы сохраняются в `queue\gui_state.json`. Выдуманную базу окно отправить не даст:
проверку делает тот же код, что и у HTTP-сервера.

Что вынесено из формы:

- **технические настройки** - окно «Настройки и журнал»: куда отправлять (в очередь рядом или
  на сервер, `POST /api/task`), адрес сервера, токен, команды watcher-а, журнал доставки
  `queue\bridge.jsonl`, кнопки «Поднять watcher» / «Остановить watcher»;
- **формулировка по контракту и ход доставки** - окно подробностей задачи (двойной щелчок по
  строке): она собирается тем же `integration\task.py`, но в форме ее показывать не нужно.

Внешний вид задан не системной темой, а своим набором виджетов `gui\ui_kit.py` (палитра,
карточки, скруглённые кнопки, пилюли состояния, перекрашенные стили ttk) - зависимостей кроме
`tkinter` нет.

Ответ читается из очереди (`queue\outbox`) либо с сервера: в режиме сервера окно опрашивает
`GET /api/tasks` и `GET /api/result/<id>`, поэтому на машине заказчика своя очередь не нужна.
Своего протокола у окна нет: оно отправитель и читатель очереди, задача всё равно проходит
через `integration\task.py`.

## 11. Установка и запуск

```
powershell -NoProfile -ExecutionPolicy Bypass -File .\deploy\install-local.ps1
```

Скрипт проверяет `py -3` и `tkinter`, создаёт каталоги очереди, копирует
`deploy\config.example.json` в `deploy\config.json` (правят копию: она в git не уходит) и по
умолчанию делает ярлыки на рабочем столе для окна задач и watcher-а (ключ `-NoShortcuts`
отменяет).

| Что запускать | Зачем |
|---------------|-------|
| `scripts\start-watcher.ps1` | поднять watcher очереди фоном: разбор журнала и передача задач в Cline; работает, пока его не погасят |
| `scripts\stop-watcher.ps1` | погасить watcher, снять pid-файл и замок; очередь не чистится |
| `deploy\run-watcher.bat` | тот же watcher в своём окне консоли (ручной путь: видны строки проходов) |
| `deploy\run-gui.bat` | поставить задачу и прочитать результат |
| `deploy\run-agent.bat` | один проход агента: взять задачу из inbox и доставить её |
| `deploy\run-server.bat` | HTTP-интерфейс для проверки и внешних отправителей |

`start-watcher.ps1` идемпотентен: живой watcher ищется по процессам с `integration\watcher.py`
в командной строке, повторный запуск поднимает второй только с ключом `-Force` (он гасит старый
через `stop-watcher.ps1`). Режим, интервал и вебхук скрипт читает из `deploy\config.json`,
а поля `root` и `python` из того же файла перекрывают значения по умолчанию (корень - путь выше
`scripts\`, интерпретатор - `py -3`). Журнал запуска - `logs\watcher.log`, ошибки -
`logs\watcher.err.log` (каталог `logs\` в git не хранится).

Обёртки `deploy\run-*.bat` берут корень харнесса из своего расположения (`%~dp0..`), поэтому
запускать их можно откуда угодно. Из настроек они читают `server.host`, `server.port`,
`server.token` (сервер) и `watcher.deliver`, `watcher.interval`, `watcher.webhook_url` (watcher).
Поле `watcher.timeout_s` пока зарезервировано: обёртки его не читают - порог застревания берётся
из `timeout_s` самой задачи (по умолчанию 1800 с).

Развёртывание слоя на нескольких машинах (машина с Cline, сервер заявок, окно на машине
заказчика) - раздел 8 [README.md](../README.md).

## 12. Проверка цепочки и границы

Проверка без Cline (ничего не открывается, работают файлы и журналы):

```
py -3 integration\agent.py --list
py -3 integration\agent.py --submit --role "инженер харнесса" --action "<действие>" --goal "<цель>" --mode harness --deliver echo
py -3 integration\watcher.py --deliver echo
py -3 integration\agent.py --process --deliver echo --json
```

`--list` печатает каталог очереди, размер журнала, позицию чтения и счётчики состояний;
`--submit` проверяет формулировку и кладёт задачу в журнал, не доставляя её. Между
постановкой и доставкой обязателен проход watcher-а: `--process` берёт задачи из `queue\inbox`,
а туда их кладёт только разбор журнала. `--deliver echo` означает, что Cline не вызывается
(тестовый режим), проверяются файлы очереди. Итог по задаче закрывается заполнением
`queue\answers\answer_<id>.md` и вызовом `--write-result`.

Границы слоя:

- **Windows**: режимы `uri` и `lg-task` открывают URI через `os.startfile`; на другой платформе
  остаются `manual` и `echo`;
- **одна задача за раз**: Cline не ведёт две задачи одновременно, очередь последовательная;
- **один watcher**: второй процесс отвергается замком `queue\.watcher.lock`, замок убитого
  процесса снимается по возрасту (две минуты);
- **очередь не в git**: `queue\` - состояние обмена задачами, а не исходники; на новой машине
  она создаётся заново;
- **`delivered` - не выполнение**: это значит, что задача передана в Cline; выполненной она
  считается только после `--write-result`;
- **`tkinter` нужен только окну**: без него очередь, HTTP и watcher работают - это проверяет
  `deploy\install-local.ps1` и печатает предупреждение.
