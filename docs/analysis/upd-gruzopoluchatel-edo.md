# УПД: почему грузополучатель виден в печатной форме, но пуст в форме электронного документа ЭДО

Разбор по коду конфигурации КомплекснаяАвтоматизация (выгрузка `dump\КомплекснаяАвтоматизация`,
репозиторий индекса `ka2`, конфигурация 2.5.27.61). Живая база не использовалась.

## Вопрос

Почему грузополучатель выводится в обычной печатной форме УПД, но не выводится на форме УПД,
которую открывает команда ЭДО "Посмотреть электронный документ" (обмен через ЕИС)?

## Короткий ответ

Это не ошибка печати и не потеря реквизита. Две формы строятся из **разных источников данных**:

| Форма | Источник данных грузополучателя | Кто заполняет |
|---|---|---|
| Обычная печатная форма УПД | реквизиты документа 1С (Грузополучатель, адрес доставки) | код: `Обработки.ПечатьОбщихФорм.ЗаполнитьРеквизитыШапкиУПД` (условие вывода `ЕстьГрузополучатель = Не ДанныеПечати.ТолькоУслуги`) |
| Форма ЭД в ЭДО ("Посмотреть электронный документ") | узел `СвСчФакт/ГрузПолуч` в XML-файле электронного документа | XSLT-преобразование XML в табличный документ (правило приходит из сервиса, в конфигурации его текста нет) |

На форме ЭД грузополучатель **не дозаполняется кодом 1С**: он там ровно такой, каким попал в XML
при формировании электронного документа. Нет узла `ГрузПолуч` в XML - строка на форме пуста.

Текстов XSL-правил в конфигурации нет: они приходят извне (сервис 1С-ЭДО) в регистр
`РегистрСведений.ПравилаПреобразованияФорматов`; описание форматов обновляют
`КонвертацияЭДО.ОбновитьОписаниеФорматовДляПреобразования` и `ОбновитьПравилоПреобразования`,
состояние - `Константа.ДатаЗагрузкиОписанияФорматовДляПреобразования`, `РегистрСведений.ФорматыДляПреобразования`.
Поэтому отрисовка задается данными регистра, а не кодом BSL.

Дополнительно: табличные макеты `DataProcessor.ОбменСКонтрагентами.Template.УПД_ИнформацияПродавца_2019`,
`_5_01`, `_5_02`, `_5_03` - это описание структуры данных электронного документа (пути XDTO плюс
заголовки граф), которое подключается через `ДеревоЭлектронногоДокументаБЭД.ДеревоЭлектронногоДокумента`.
В них указано, в каких узлах лежат данные: заголовок "Грузополучатель" - в макете `_5_03` (строка 5511),
путь `Файл.Документ.СвСчФакт.ГрузПолуч` - в макете `_5_01` (строка 22607).

## 2. Как грузополучатель попадает в XML исходящего электронного документа

Общая точка входа - переопределяемый метод `ОбменСКонтрагентамиПереопределяемый.ЗаполнитьДанныеУПД...`,
реализация - в общем модуле `CommonModules/ОбменСКонтрагентамиУТ/Ext/Module.bsl`.

### 2.1. Формат 2019 (`ЗаполнитьДанныеПервичногоДокументаУПД_2019`, L15637-16673)

Фрагмент около L15973-16003 - данные грузополучателя собираются **только при заполненном реквизите**:

```bsl
// Выводим данные грузополучателя.
ТаблицаГрузополучателей = ЭлектронноеВзаимодействие.ДанныеЭлементаДереваЭлектронногоДокумента(ДеревоДанных, "СведенияОГрузополучателе");
ТаблицаГрузополучателей.Колонки.Добавить("СведенияОбУчастнике");

Если Не ДанныеШапки.ТолькоУслуги Тогда
    СведенияОГрузополучателе = "";
    ...
    Если НЕ ЕстьТаблицаРезультатПоКонтрагентам Тогда
        Если ДанныеШапки.Грузополучатель <> Неопределено Тогда
            СведенияОГрузополучателе = ЭлектронноеВзаимодействиеУТ.ПолучитьДанныеЮрФизЛица(ДанныеШапки.Грузополучатель, БанковскийСчетГрузополучателя, ДанныеШапки.Дата);
        КонецЕсли;
    ИначеЕсли ЗначениеЗаполнено(ДанныеКонтрагента.Грузополучатель) Тогда
        СведенияОГрузополучателе = ЭлектронноеВзаимодействиеУТ.ПолучитьДанныеЮрФизЛица(ДанныеКонтрагента.Грузополучатель, БанковскийСчетГрузополучателя, ДанныеШапки.Дата);
    КонецЕсли;
    Если ЗначениеЗаполнено(СведенияОГрузополучателе) Тогда
        ДанныеГрузополучателя = ПолучитьДанныеУчастникаУПД(СведенияОГрузополучателе, "Факт");
        ...
        СтрокаГрузополучателя = ТаблицаГрузополучателей.Добавить();
        ЗаполнитьЗначенияСвойств(СтрокаГрузополучателя, ДанныеГрузополучателя);
    КонецЕсли;
    ДобавитьОбработкуОшибокВТаблицуУчастниковУПД(ТаблицаГрузополучателей);
    ЭлектронноеВзаимодействие.ЗагрузитьТаблицуВДерево(ДеревоДанных, ТаблицаГрузополучателей, "СведенияОГрузополучателе");
КонецЕсли;
```

Ключевые условия: `Не ДанныеШапки.ТолькоУслуги`, выбор источника по флагу `ЕстьТаблицаРезультатПоКонтрагентам`
(`ДанныеШапки.Грузополучатель` против `ДанныеКонтрагента.Грузополучатель`) и проверка
`ЗначениеЗаполнено(СведенияОГрузополучателе)` - пусто, значит строка в дерево не добавляется.
Адрес берут из адреса доставки только при `ПродажиСервер.АдресГрузополучателяБратьИзАдресаДоставки(Документ)`.

### 2.2. Формат 5.02 (`ЗаполнитьДанныеПервичногоДокументаУПД_5_02`, L11870-13275)

Фрагмент около L12290-12315 - здесь есть **подстановка покупателя** при пустом грузополучателе:

```bsl
// Выводим данные грузополучателя.
Если Не ДанныеШапки.ТолькоУслуги Тогда
    ПутьТаблицы = "СведенияОСчетеФактуре.СведенияОГрузополучателях";
    ИмяУчастника = "Грузополучатель";
    СведенияОГрузополучателе = Неопределено;
    ...
    Если НЕ ЕстьТаблицаРезультатПоКонтрагентам Тогда
        Если ЗначениеЗаполнено(ДанныеШапки.Грузополучатель) Тогда
            СведенияОГрузополучателе = ЭлектронноеВзаимодействиеУТ.ПолучитьДанныеЮрФизЛица(ДанныеШапки.Грузополучатель, БанковскийСчетГрузополучателя, ДанныеШапки.Дата);
        Иначе
            СведенияОГрузополучателе = СведенияОПокупателе;
            Если ЗначениеЗаполнено(ДанныеШапки.АдресДоставкиЗначенияПолей) Тогда
                СведенияОГрузополучателе.Вставить("ПроизвольныйАдрес", ДанныеШапки.АдресДоставкиЗначенияПолей);
            КонецЕсли;
        КонецЕсли;
    ИначеЕсли ЗначениеЗаполнено(ДанныеКонтрагента.Грузополучатель) Тогда
        ...
    КонецЕсли;
    ...
    Если ЭтоЭлектронноеАктированиеЕИС Тогда
        ИдентификаторУчастника = ЭлектронноеАктированиеЕИС.НачальныйИндексИнформацииУчастникаГрузополучателя();
        СтрокаГрузополучателя[ИмяУчастника].ИнформацияДляУчастника = ИдентификаторУчастника;
        ...
```

**Разница между форматами:** в 5.02/5.03 при пустом реквизите грузополучателя в XML все равно попадает
участник (покупатель), в 2019 - не попадает ничего.

различается только источник данных.

Фрагмент около L20672-20684 - та же логика: нет узла, нет данных:

```bsl

Если СписокГрузПолуч <> Неопределено Тогда
```

Вывод раздела: и запись, и чтение подчинены одному условию - наличию узла `Документ.СвСчФакт.ГрузПолуч`.

## 3. Почему именно обмен через ЕИС дает пустого грузополучателя

Найдена ветка, которая **сознательно удаляет** грузополучателя из формируемого документа:
`CommonModules/ЭлектронноеАктированиеЕИС/Ext/Module.bsl`.

Точка входа - `ПередФормированиемЭлектронногоДокумента` (L4245-4260): при пространстве имен
ON_NSCHFDOPPR (электронное актирование ЕИС) вызываются `ПроверитьГрузополучателей` (L4083-4151)
или `ПроверитьГрузополучателей_5_02` (L4159-4227). В комментариях кода причина названа прямо:
совпадение ИНН и КПП покупателя и грузополучателя нарушает правило РДИК_0507, поэтому грузополучатель
удаляется, а место поставки заменяется индексом информации покупателя. Индексы заданы рядом
(L269-273): `НачальныйИндексИнформацииУчастникаПокупателя` = "0",
`НачальныйИндексИнформацииУчастникаГрузополучателя` = "1".

Включение режима - `Константа.ИспользоватьЭлектронноеАктированиеВЕИС` через функцию
`ИспользоватьЭлектронноеАктированиеВЕИС()` (L2439-2453). Факт вызова из формирования УПД подтвержден:
`ФорматыЭДО_ФНС.ЗаполнитьДокумент_УПД2019_ИнформацияПродавца` (L4128-4146) вызывает
`ПередФормированиемЭлектронногоДокумента` при `ДанныеЭлектронногоАктированияЕИС = Истина`.

Сценарий расхождения целиком:

1. В документе реквизит `Грузополучатель` заполнен обычным способом (адрес доставки контрагента).
2. Печатная форма УПД берет данные из реквизитов и печатает строку.
3. При формировании ЭД режим электронного актирования ЕИС включен и ИНН+КПП грузополучателя
   совпадают с покупателем (частый случай, когда отдельный контрагент под адрес доставки не заведен):
   фильтр `ПроверитьГрузополучателей` удаляет участника из XML.
4. На форме ЭД (XSLT по XML) узел `СвСчФакт/ГрузПолуч` отсутствует, поэтому строка пуста.

## 4. Печатная форма УПД: другой источник (для сравнения)

Обычная печатная форма УПД собирается не из XML и не из дерева ЭД, а напрямую из реквизитов документа:
`DataProcessors/ПечатьОбщихФорм/Ext/ManagerModule.bsl`, процедура `ЗаполнитьРеквизитыШапкиУПД` (L3673-3920),
работа с грузополучателем - около L3829, L3860, L3897. Условие вывода в шапке -
`ЕстьГрузополучатель = Не ДанныеПечати.ТолькоУслуги` (то же условие, что и при формировании XML,
но источник данных - реквизиты, а не XML).

Отсюда практический вывод, полезный при разборе жалоб на УПД:

| Проверяемый признак | Печатная форма | Форма электронного документа |
|---|---|---|
| Источник данных | реквизиты документа (Грузополучатель, адрес доставки) | узел `СвСчФакт/ГрузПолуч` в XML файла сообщения |
| Чем рисуется | код BSL (`ЗаполнитьРеквизитыШапкиУПД`) | XSLT-преобразование XML (правило из сервиса, регистр `ПравилаПреобразованияФорматов`) |
| Может ли код 1С дозаполнить | да, берет актуальные реквизиты | нет, показывает то, что в файле |
| Что значит "пусто" | реквизит не заполнен | узла нет в XML (не был сформирован или удален фильтром) |

Важно: в конфигурациях на БСП состав печатных форм регистрируется кодом модуля менеджера
(процедура `Печать`), а не объектами метаданных, поэтому перечень печатных форм документа
по метаданным не виден. Это уже отмечено в журнале харнесса.

## 5. Что проверить в базе заказчика, чтобы подтвердить причину на живых данных

Разбор сделан по выгрузке, без живой базы. Порядок проверки:

1. Включен ли режим электронного актирования ЕИС: `Константа.ИспользоватьЭлектронноеАктированиеВЕИС`
   и признак электронного актирования ЕИС у самого документа. При Истине работает фильтр
   `ПроверитьГрузополучателей`, который удаляет совпадающего с покупателем грузополучателя.
2. Совпадают ли ИНН и КПП грузополучателя и покупателя в документе-основании (при совпадении
   фильтр срабатывает по правилу РДИК_0507).
3. Реквизиты документа-основания: `Грузополучатель`, `АдресДоставки` и флаг
   `ЕстьТаблицаРезультатПоКонтрагентам` (он переключает источник между
   `ДанныеШапки.Грузополучатель` и `ДанныеКонтрагента.Грузополучатель`).
4. Формат электронного документа: 2019 или 5.02/5.03. В 2019 пустой реквизит дает отсутствие узла,
   в 5.02/5.03 участник подставляется из покупателя.
5. Наличие узла в самом файле: искать в XML основного файла сообщения узел `СвСчФакт/ГрузПолуч`
   (`Документ.СвСчФакт.ГрузПолуч`). Узла нет - причина подтверждена, и это не дефект показа.
6. Правило визуализации на месте (иначе форма ЭД вообще не построится):

```sql
ВЫБРАТЬ ПЕРВЫЕ 20 *
ИЗ РегистрСведений.ПравилаПреобразованияФорматов
ГДЕ ИтоговыйФормат = "ТабличныйДокумент"
```

7. Кэш визуализации: если XML в сообщении правили, а форма показывает старое, помогает
   управление кэшем `РегистрСведений.КэшВизуализацииДокументовЭДО`
   (признак `ТребуетсяОбновить`, обновление - `ОбновитьКэшВизуализации`,
   регламентное задание `ПолучитьДанныеВизуализацииЭДО`). К случаю пустого грузополучателя это
   относится только как проверка версии: строка пуста не из-за кэша, а из-за отсутствия узла в XML.

## 6. Ограничения этого разбора

- Живая база заказчика недоступна (закрытый контур), данные конкретного электронного документа
  не проверялись: вывод следует из кода, а не из воспроизведения на данных.
- Текстов XSL-правил преобразования в конфигурации нет (они загружаются из сервиса в регистр),
  поэтому точный вид ячейки "Грузополучатель" на форме по выгрузке не проверяется.
- Выгрузка не содержит расширения `InfostartToolkitCORP`; в базе также работает подключенное
  расширение, поэтому модули расширения с префиксом ИТК в разбор не вошли.
- В индексе присутствует только основная конфигурация версии 2.5.27.61. Для другой версии
  конфигурации заказчика номера строк могут отличаться, смысл процедур - нет.
- Ограничение инструмента: очень крупные модули ЭДО (размером в мегабайты) недоступны обычному
  поиску по тексту, поэтому к ним применялся прямой разбор по таблице функций индекса и чтение
  диапазонов строк.
