# Возможности и границы

Документ отвечает на два вопроса: что харнесс умеет и где он упирается в стену.
Границы нужно называть вслух, а не обходить формулировками.

## Слой 1. Живая база (`1c-toolkit`)

**Что даёт.** Факты о состоянии конкретной информационной базы: данные, метаданные
как они есть сейчас, выполнение произвольного кода BSL, журнал регистрации, права
доступа, ссылки на объекты, подсказки по синтаксису BSL.

**Что закрывает.**

- прочитать данные (запрос, поиск объекта по ссылке);
- **изменить данные и увидеть результат** (записать, провести, перепровести);
- выполнить фрагмент кода в контексте базы;
- получить состав и структуру метаданных;
- работать с OData и HTTP-сервисами опубликованной базы;
- журнал регистрации, права роли, поиск ссылок на объект.

**Границы.**

- сервер поднимается вручную, **на одну базу за раз** - переключение базы требует
  переключения сервера;
- нужен запущенный 1С:Предприятие;
- «встроенный сервер» не заменяет отладчик: пошаговой отладки нет;
- выполнение произвольного кода - операция с последствиями; деструктивные действия
  выполняются только по явной задаче пользователя.

## Слой 2. Индекс кода (`1c-code-index`)

**Что даёт.** Структурный разбор выгрузки конфигурации (XML Конфигуратора или
`.mdo` из EDT): состав объектов, реквизиты с типами, формы и их обработчики,
подписки на события, регистраторы регистров, граф вызовов, граф связей данных,
права ролей, произвольный read-only SQL по метаданным и графам.

**Что закрывает.**

- «из чего состоит объект X» без запуска платформы;
- «кто вызывает эту процедуру» и «что она вызывает»;
- «какие формы у объекта и какие у них обработчики»;
- «в какие регистры пишет этот документ»;
- ревью кода и навигация по большой выгрузке.

**Границы.**

- работает **по выгрузке**, а не по базе. Расхождение выгрузки и базы - источник
  неверных выводов; агент обязан это оговаривать;
- выгрузка обязана существовать в каталоге проекта (в репозитории как алиас `main`).
  Если выгрузки нет - слой недоступен;
- не отвечает на вопросы про данные.

## Слой 3. Справка платформы (`1c-platform-help`)

**Что даёт.** Документацию API платформы из `shcntx_ru.hbk`: существование метода,
его сигнатуры, типы параметров и возвращаемого значения; стандарты кода BSL и
строгую типизацию.

**Что закрывает.**

- «есть ли у платформы такой метод и как он вызывается»;
- «какие свойства у типа X»;
- «как принято писать по стандартам 1С».

**Границы.**

- источник - файл справки установленной платформы. В 8.3.25 файла `shcntx_ru.hbk`
  нет; сервер нацелен на 8.3.27;
- semantic-поиск не включён (нужен `torch` и модели-эмбеддер, это гигабайты);
  доступен keyword-режим;
- это не источник фактов о конкретной конфигурации - только о платформе.

## Слой 4. Скиллы (`.cline/skills`, 206 штук)

**Что даёт.** Готовые процедуры и форматы: сборка и разбор объектов метаданных,
форм, ролей, СКД, макетов, XDTO, подсистем; работа с базами (создать, выгрузить,
загрузить, обновить, запустить); расширения и внешние обработки; веб-публикация и
тесты в браузере; Gherkin и Vanessa Automation; офлайн-валидаторы; справочники
БСП, ЗУП, SSL-сценариев; стандарты BSL и паттерны.

**Что закрывает.**

- рутину правки и сборки объектов по формату платформы (а не поиском по тексту);
- валидацию результата **без** платформы и Docker;
- написание и прогон сценариев автотестов.

**Границы.**

- валидаторы скиллов проверяют **имена и структуру**, но не типы выражений,
  семантику BSL и план запроса;
- наборы скиллов перекрываются: cc-1c-skills даёт имена без префикса (`cf-edit`),
  cursor-1c-skills - с префиксом `1c-` (`1c-cf-edit`). При совпадении имени
  каталога побеждает cursor-набор (порядок в `install-vendor-skills.ps1`).

## Слой 5. Внешняя интеграция (`integration/`, `deploy/`)

**Что даёт.** Канал, через который задачу ставит не человек в чате, а внешняя система:
страница задач в браузере или HTTP-клиент. Формат задачи тот же (слоты роль, действие,
база, цель), но ответ возвращается не в чат, а в очередь на сервере.

**Что закрывает.**

- поставить задачу без чата: страница `integration\web\`, `POST /api/task`;
- видеть стадии: `queued`, `claimed`, `delivered`, `running`, `done` - их считает сервер;
- получить машиночитаемый результат: `outbox` по схеме `result_schema.json`;
- связать харнесс с внешней системой: WSGI-приложение для хостинга (Passenger), ключи
  клиентов, очередь с одним владельцем записи.

**Границы.**

- это **не источник фактов о базе**: слой только доставляет задачу и возвращает ответ, факты
  берутся теми же слоями 1-3 (живая база, индекс кода, справка платформы);
- очередь последовательная: Cline ведёт одну задачу за раз, а стадия `delivered` означает
  «передано», а не «выполнено»;
- доставка режимами `uri` и `manual` работает только в Windows (`os.startfile`);
- очередь живёт на сервере (`server.root`), на машине агента остаётся только
  `temp\queue\<id>\` на время задачи;
- `tkinter` слою не нужен: страница задач - обычный HTML без сборки и внешних CDN.

Устройство, контракты и границы подробно - `docs\07-external-integration.md`.

## Чего нет на машине и что из этого следует

| Нет | Следствие |
|-----|-----------|
| Docker | `1C_SyntaxChecker` и Docker-режим toolkit недоступны; валидация - только офлайн-валидаторами |
| 1С 7.7 | задачи по 77 не выполнять, сообщать о невозможности |
| Node.js / npx | npm-обёртки и `mcp-remote` недоступны |
| Java | инструменты на JVM (в т.ч. оригинальный Kotlin-сервер справки) недоступны |
| СУБД-сервер 1С | только файловые базы; клиент-серверные задачи требуют реквизитов СУБД |

## Сводка: что спросить, куда идти

| Вопрос | Слой |
|--------|------|
| что в базе сейчас | живая база |
| изменить и подтвердить | живая база |
| из чего состоит объект в конфигурации | индекс кода |
| кто вызывает процедуру | индекс кода |
| существует ли метод платформы | справка платформы |
| как собрать/разобрать/проверить артефакт | скиллы |
| путь и платформа базы | `.v8-project.json` |
| поставить задачу без чата и прочитать ответ | внешняя интеграция (`integration/`, `deploy/`, `queue/` на сервере) |
