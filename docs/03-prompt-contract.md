# Контракт задачи: формат и ответ агента

## Формат постановки

```
как <роль> сделай <действие> в базе <база> чтобы <цель> по START.md
```

Это не пример, а основной принимаемый формат. Он нужен, чтобы задача была
однозначно разбираемой: роль указывает приоритетный слой, база - слой живой базы,
цель - критерий проверки.

Второй формат - задача по самому харнессу (инструменту агента), без базы:

```
как инженер харнесса сделай <действие> чтобы <цель> по START.md
```

Различение простое: названа база 1С - задача по базе; правится инструмент агента
(правило, скрипт, док, формат задачи) - задача по харнессу. Границы класса задач -
`.clinerules/50-harness.md`.

### Слот `<база>`

Допустимые формы:

- `File="C:\Users\art8k\OneDrive\Документы\1C\DemoARAutomation20"` - точный путь;
- `C:\...\DemoARAutomation20` - путь без обёртки `File=`;
- `демо`, `erp`, `ssl`, `автоматизация` - алиас из `.v8-project.json`;
- `DemoARAutomation20` - `id` или `name` записи.

Разрешение: `.v8-project.json` -> `databases[]`. При неоднозначности агент
спрашивает, а не выбирает наугад.

### Слот `<роль>`

Роль не обязана быть «должностью». Это указание, на каком слое работать:

| Роль (пример) | Приоритетный слой |
|---------------|-------------------|
| программист 1С | индекс кода + скиллы сборки/валидации |
| тестировщик | скиллы Gherkin/Vanessa + живая база для прогона |
| аналитик | живая база (метаданные) + индекс кода |
| администратор | скиллы `db-*`, `web-*` + живая база |
| инженер харнесса (агент развития) | файлы проекта: правила, доки, `scripts\*` + git (коммит и отправка в `origin`) |

Роль - не переключатель. Cline не поддерживает cursor-семантику `globs`/`alwaysApply`,
поэтому все файлы правил активны всегда, а скиллы выбираются по релевантности задачи.
Роль задаёт приоритет работы и обязательные проверки, а не список подключаемых скиллов.

**Git - только у инженера харнесса.** Это единственная роль, работающая с репозиторием,
и её задача не считается законченной, пока правки не на GitHub: `git status -sb`,
`git add` изменённых файлов проекта, `git commit`, `git push --quiet origin main`, затем
сверка `git ls-remote origin refs/heads/main` с `git rev-parse HEAD`
(`.clinerules/50-harness.md`, п.3). В задачах остальных ролей git не трогается никогда:
результат работы с базой 1С в репозиторий харнесса не идёт, разбор кейса сохраняется
файлом в `analysis\` (каталог в `.gitignore`).

## Обязательный ответ агента

### Первый блок - преамбула

```
Слой: <слой или слои>
MCP: <инструменты, которые будут вызваны>
Скиллы: <скиллы, которые будут прочитаны>
Проверка: <чем подтвердится результат>
```

Назначение: пользователь до начала работы видит, какими средствами будет решаться
задача, и может поправить выбор. Преамбула из четырёх строк - не украшение, а
точка контроля.

### Последний блок - отчёт

```
Сделано: <что изменено или получено; пути, имена объектов>
Проверка: <средство и его фактический вывод>
Не проверено: <что осталось вне проверки и почему>
```

Если задача была **разбором** (анализом), в строке «Сделано» называется путь файла
`analysis\<ГГГГ-ММ-ДД>_<ЧЧММ>_<краткое-имя>.md`: результат анализа сохраняется в
`analysis\` (заводит `scripts\new-analysis.ps1`), а не растворяется в переписке.
Каталог закрыт `.gitignore` - разбор не коммитится.

## Пример полного обмена

**Пользователь:**

```
как аналитик сделай описание структуры документа ПоступлениеТоваровУслуг в базе erp
чтобы понять его движения по регистрам по START.md
```

**Агент:**

```
Слой: живая база (метаданные) + индекс кода (движения и связи)
MCP: 1c-toolkit (get_metadata), 1c-code-index (get_object_structure, get_register_writers)
Скиллы: не требуется (задача на чтение)
Проверка: сверка перечня регистров из get_register_writers с составом движений по метаданным
```

...работа...

```
Сделано: описан документ ПоступлениеТоваровУслуг; реквизиты - из get_object_structure,
табличные части - ..., движения - по регистрам ...
Проверка: 1c-code-index.get_register_writers вернул N регистров; состав совпал
с ответом 1c-toolkit.get_metadata (список совпадает)
Не проверено: типы значений и порядок движений в конкретных проведённых документах -
это требует запроса по данным, задача на чтение структуры
```

## Запреты, вытекающие из формата

1. Работа без преамбулы.
2. Преамбула «на отвяжись»: `MCP: не требуется` там, где нужны данные базы.
3. `Проверка: проверю глазами` - проверка обязана называть инструмент.
4. Ответ на задачу не в формате: вместо переформулировки агент начинает угадывать
   роль и базу.
5. Смешение слоёв: данные берутся из индекса кода, структура - «по памяти».
6. Задача по харнессу решена без прогона `scripts\check-harness.ps1` и
   `scripts\check-docs.ps1` - расхождение доков с фактом остаётся незамеченным.
7. Задача по базе 1С завершилась коммитом в репозиторий харнесса: коммитить в задачах
   по базе нельзя никогда (`.clinerules/00-contract.md`, п.4).
8. Задача по харнессу оставлена локально: правки не закоммичены или не отправлены в
   `origin` (`.clinerules/50-harness.md`, п.3).

## Почему это работает

Формат решает три проблемы, из-за которых агент на 1С обычно врёт:

- **что делать** - роль и действие задают область, а не оставляют её на догадку;
- **где брать факты** - база в задаче заставляет идти в живой слой, а не в память;
- **как проверить** - цель превращается в конкретное средство проверки, названное
  до начала работы.

## Бюджет контекста

Что уходит в каждый запрос к модели и потому оплачивается каждой репликой (замер
`scripts\check-context.ps1`, 2026-10-14):

| Часть | Как попадает | Символов |
|-------|--------------|----------|
| `.clinerules\*.md` (шесть файлов) | целиком, всегда | 43 474 |
| `AGENTS.md` | целиком, всегда | 2 677 |
| метаданные скиллов (206) | всегда; тело `SKILL.md` - по релевантности | 3 118 | <!-- check-docs:ignore: 3 118 - это символы, а не число скиллов -->
| схемы MCP-инструментов (три сервера) | всегда | около 109 000 |
| `START.md`, `README.md`, `SOURCES.md`, `docs\`, `analysis\` | не инжектируются | - |

Текстовый префикс - 49 269 символов, около 17 500 токенов в оценке прибора: кириллица в
токенизаторах плотнее латиницы, символ русского текста стоит примерно вдвое дороже
английского. До реструктуризации 2026-10-14 тот же префикс занимал 86 772 символа (около
31 000 токенов), и из них один `40-lessons.md` - 53 323 символа: журнал пересказывал
разборы, которые и без него лежат в `analysis\`.

Cline 4.1.24 подключает файлы правил целиком и всегда: ленивых правил, `alwaysApply` и
`globs` у него нет (у файла есть только `disabled`). Скиллы ленивы по природе - в контекст
идут только метаданные, тело читается по релевантности. Список MCP-инструментов правится
ключом `disabledTools` в настройках сервера.

Бюджеты (проверяет `scripts\check-context.ps1`, он же вызывается из `check-harness.ps1`):
`.clinerules` - 45 000 символов, `40-lessons.md` - 15 500, `AGENTS.md` - 3 000, метаданные
скиллов - 6 000. <!-- check-docs:ignore: 6 000 - это бюджет символов, а не число скиллов -->
Смысл бюджета - запрет на возврат, а не минимум любой ценой: правило, инструкция и разбор
кейса живут в разных местах, и разбор кейса в правилах не задерживается.
