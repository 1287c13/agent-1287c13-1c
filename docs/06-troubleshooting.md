# Диагностика и частые проблемы

Первым делом:

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File .\scripts\check-harness.ps1
```

Скрипт печатает `[ok]` / `[warn]` / `[FAIL]` по каждому пункту и возвращает код 1,
если что-то требует действия.

---

## MCP

### Cline не видит MCP-серверы

**Причина.** VS Code не перезапускали после `enable-mcp.ps1`, либо переменная не
установилась.

**Проверка:**
```powershell
[Environment]::GetEnvironmentVariable('CLINE_MCP_SETTINGS_PATH','User')
```
Должен вернуть `<проект>\.cline\cline_mcp_settings.json`.

**Лечение:** выполнить `scripts\enable-mcp.ps1`, затем **полностью** закрыть
VS Code (все окна) и открыть заново.

### Сервер `1c-code-index` не поднимается

**Симптом:** инструменты отдают `daemon_offline` или «путь не отслеживается демоном».

**Причина:** не запущен фоновый индексатор, либо у сервера и демона разные
`CODE_INDEX_HOME`.

**Лечение:** `scripts\start-harness.ps1`. Проверка:
```powershell
$env:CODE_INDEX_HOME = "C:\_works\1c-ai\agent\.cline\mcp\code-index-mcp\home"
& "C:\_works\1c-ai\agent\.cline\mcp\code-index-mcp\bsl-indexer.exe" daemon status
```
Папка проекта должна быть в статусе `ready`. Первичная индексация видна в
`home\daemon.log`.

**`not_started` / `unknown_repo`** - каталог не попал в `daemon.toml`. Проверить
секцию `[[paths]]` и выполнить `bsl-indexer.exe daemon reload`.

**Чем не проверять живость.** `get_stats` - не признак живого демона: он читает
`.code-index\index.db` напрямую и считает статистику около 9 с на репозиторий (а без
параметра `repo` - по всем репозиториям сразу). Список репозиториев и их состояния
показывает `scripts\check-harness.ps1`: алиасы - из `daemon.toml`, статусы - из
`GET http://127.0.0.1:8015/health` (0,05 с).

**`serve` - это ещё не демон.** `bsl-indexer.exe serve` (его запускает Cline по stdio)
читает индекс сам, а инструменты данных спрашивают демон (`http://127.0.0.1:8015`): без
демона они отвечают `daemon_offline` либо `not_started`, хотя `get_stats` и `health`
работают - они читают `.code-index\index.db` напрямую. После запуска демон сверяет время
и размер файлов во всех отслеживаемых путях: `main` (124 954 файла) - 307 с, путь выгрузки
ждал очереди и только затем пошёл в `initial_indexing`. Всё это время инструменты по
выгрузке недоступны; ждать, а не переиндексировать.

### Живая база: порт 6003 не отвечает

**Симптом:** инструменты `1c-toolkit` недоступны, `check-harness.ps1` пишет
`[warn] порт 6003 не отвечает`.

**Лечение:** поднять сеанс toolkit скриптом (база берётся из `.v8-project.json`):
```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File .\scripts\start-toolkit.ps1
```
Скрипт открывает `.cline\mcp\1c-mcp-toolkit\MCP_Toolkit.epf` в базе и включает встроенный
сервер автозапуском обработки, затем ждёт `/health`. Если сервер не поднимается: база
занята чужим клиентским сеансом (лицензия) либо порт держит другой сеанс toolkit -
освобождает `scripts\stop-toolkit.ps1`. Проверка:
```powershell
Invoke-WebRequest http://127.0.0.1:6003/health -UseBasicParsing
```

Второй сеанс скрипт не поднимает: если сеанс 1С с обработкой уже запущен, а `/health`
молчит, он ждёт готовности этого сеанса и пишет PID. Перезапуск такого сеанса -
`scripts\start-toolkit.ps1 -Force` (скрипт сначала гасит старый сеанс). Если ждать нечего
и сервер не поднимается, смотреть окно 1С: диалог входа, чужие клиентские сеансы базы
(лицензия на клиентов), вторая обработка на том же порту.

### Инструменты `1c-toolkit` не появились в сеансе

**Симптом:** порт 6003 отвечает на `/health`, но инструментов `1c-toolkit` в сеансе нет -
сервер `streamableHttp` подняли уже после старта VS Code.

**Что делать:** перезапускать VS Code не обязательно, у обработки есть документированный
REST API (`skills-vendor\1c-mcp-toolkit\README_FULL.md`, раздел «REST API»):
`POST http://127.0.0.1:6003/api/execute_code` (тело `{"code": "..."}`, результат - в
переменной `Результат`), `/api/execute_query`, `/api/get_object_by_link`,
`/api/get_metadata`. Тело собирать `ConvertTo-Json` и отдавать как UTF-8, ответ читать
тоже как UTF-8 (`RawContentStream`) - иначе кириллица приходит кракозябрами.

### Сервер справки не находит данные

**Симптом:** `1c-platform-help` отвечает ошибкой или пустым результатом.

**Причина:** в каталоге платформы нет файла `shcntx_ru.hbk`. В версии 8.3.25 его нет.

**Лечение:** в `.cline\cline_mcp_settings.json` в аргументе `-p` указать
`C:\Program Files\1cv8\8.3.27.2130\bin` (проверить наличие `shcntx_ru.hbk`) или
`8.3.24.1819\bin`.

### Ошибка «Unsupported MCP transport»

**Причина:** в конфиге недопустимый `type`.

**Лечение:** допустимы ровно `stdio`, `sse`, `streamableHttp`.

### Автозапуск сервера toolkit (без кнопок на форме)

Сервер поднимается и из командной строки: обработка запускается в базе с ключом
`/C "autostart;<метка>;<путь к params.json>"`, по завершении пишет файл-сигнал
`signal_*.txt` со значением `ready`.

**Факты.** Порт и режим берутся из **сохранённых настроек формы** обработки, а не из
`params.json`; `params.json` задаёт только автозапуск. Проверка готовности -
`Invoke-WebRequest http://127.0.0.1:6003/health` → `{"status":"healthy","mode":"native","port":6003}`.

### Код отклоняется: «Операция запрещена: код содержит опасные ключевые слова»

**Причина.** В `MCP_Toolkit.epf` включена защита чтения/записи: `execute_code` не
принимает код с опасными ключевыми словами (например, `Записать`). Параметр
автозапуска `auto_allow_write` в `params.json` защиту **не снимает** (проверено:
передано `true`, фильтр остался включён).

**Лечение.** Снять флаг в **форме обработки** (SKILL.md скилла `1c-mcp-toolkit`,
раздел про тесты на запись). Обходные формулировки BSL запрещены; в отчёте это
идёт строкой «Не проверено». Подробнее - `.clinerules/40-lessons.md`, п.3.

### Сценарий написан, но прогон не идёт или падает

**Симптом.** `.feature` (сценарий под задачу лежит в `temp\features\` - единственное место
временных файлов, `.clinerules\00-contract.md`, п.4) валиден по реестру шагов, а
`scripts\vanessa-run.ps1` не доводит прогон до результата: либо платформа не поднимает
сеанс, либо `.vanessa\status.txt` = 1.

**Причины, в порядке проверки** (все разобраны живыми запусками,
`.clinerules/40-lessons.md`, п.12-13):

1. **Обработка Vanessa не развёрнута.** Нет `.vanessa\vanessa-automation-single.epf`.
   Vanessa запускается **внешней обработкой** платформы (ключ `/Execute`), в
   конфигурацию базы не ставится - искать её объекты через `get_metadata` по маскам
   `ванесс`/`vanessa` бессмысленно, их не будет ни в одной базе. Лечение: обработку
   разворачивает сам `scripts\vanessa-run.ps1` из свежего релизного архива в Загрузках
   (или вручную - вспомогательным `scripts\install-vanessa.ps1 -Zip <архив>`; этот файл
   локальный и в git не хранится).
2. **Нет свободного клиентского слота.** Платформа отвечает `Превышено ограничение
   лицензии для разработчиков на количество клиентов информационной базы`: прогону
   нужны **два** клиента одной базы (менеджер тестирования и клиент тестирования).
   Слот занимает любой живой клиентский сеанс, включая сервер `1C MCP Toolkit` на
   порту 6003. Лечение: прогон на базе без чужих сеансов; сеанс toolkit прогон гасит
   и возвращает сам - `scripts\vanessa-run.ps1 -FreeToolkit`.
3. **`Пользователь ИБ не идентифицирован`.** В записи базы в `.v8-project.json` не
   заданы `user`/`password` - сеанс менеджера не авторизуется. Это отдельный отказ,
   с лицензией его путать нельзя.

**Диагностика.** Порядок один: `.vanessa\status.txt` (0 - сценарии прошли, 1 - есть
упавшие) -> `.vanessa\va-log.txt` (текст ошибки упавшего шага, выполняемый код и
техданные) -> `.vanessa\junit\junit.xml` (машиночитаемый отчёт; имя файла - именно
`junit.xml`, `Steps.xml` не создаётся). Если прогон невозможен в принципе, результат
сценария ограничен валидацией по реестру шагов:
`python .cline\skills\1c-vanessa-steps\scripts\validate.py <файл>` и честной строкой
«прогон не выполнен».

### OData опубликован, но `$metadata` возвращает 404

**Симптом.** `http://localhost:8081/<база>` → 200 (веб-клиент открывается), а
`http://localhost:8081/<база>/odata/standard.odata/$metadata` → 404.

**Причина.** В конфигурациях на БСП (КА2, ERP) стандартный интерфейс OData
включается настройкой в базе: обработка `НастройкаСтандартногоИнтерфейсаOData`
заполняет `Константа.ПользовательСтандартногоИнтерфейсаOData` и роли. При пустой
константе состав публикуемых объектов пуст - сервер отдаёт 404, а не метаданные.

**Лечение.** Развернуть публикацию готовым скриптом `scripts\publish-odata.ps1`
(Apache + `default.vrd` с `enableStandardOdata="true"`), затем настроить сам интерфейс
OData в базе. Второй шаг - это запись в базу, значит упирается в защиту записи toolkit
(см. раздел выше).

## Скиллы и правила

### Скиллы не видны

**Лечение:**
```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File .\scripts\install-vendor-skills.ps1
```
Скрипт заново собирает `.cline\skills` и валидирует `name:` в frontmatter каждого
`SKILL.md`. Затем перезапустить VS Code.

### Скилл срабатывает не тот

**Лечение:** в преамбуле явно назвать скилл, которым решать, либо обратиться к
`1c-config-router`. Наборов шесть, имена частично перекрываются по смыслу.

### Правила не применяются

Правила читаются из `AGENTS.md`, `.clinerules/`, `.cursor/rules/`, `.cursorrules`.
Проверить, что файлы на месте и не пустые. Cline подключает их без перезапуска
после правки, но перезапуск полезен.

## Установка

### `install-vendor-skills.ps1` падает с `Split-Path : Cannot bind argument`

**Причина:** скрипт запущен способом, при котором `$PSScriptRoot` пуст.

**Лечение:** запускать только так:
```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File .\scripts\install-vendor-skills.ps1
```

### Любой `.ps1` с корнем из `$PSScriptRoot` в блоке `param` падает так же

**Причина:** в PowerShell 5.1 в блоке `param()` переменная `$PSScriptRoot` ещё не заполнена,
поэтому значение по умолчанию обращается к пустой строке - даже при запуске через `-File`.
Второй источник того же отказа рядом: `.ps1` с кириллицей **без BOM** разбирается как ANSI и
ломается на этом же месте.

**Лечение:** корень скрипта считать в теле, а не в `param`: `param([string] $Root = '')`, ниже
`if (-not $Root) { $Root = Split-Path -Parent $PSScriptRoot }`. Так сделано в
`scripts\check-context.ps1`. После правки - `scripts\fix-encoding.ps1`, а прогон - отдельной
командой: команды одной пачки агента выполняются параллельно и читают файл до записи BOM.

### `scripts\fix-encoding.ps1` уходит в таймаут на пустом `-Path`

**Причина:** значение по умолчанию бралось как родитель каталога скрипта, то есть корень
проекта, и `Get-ChildItem -Recurse` шёл по `dump\`, `skills-vendor\` и `.code-index\` - минуты.

**Лечение:** дефолт `-Path` - каталог скрипта (`scripts\`), широкий обход задаётся явно
(`-Path <каталог>`). Правило шире: значение по умолчанию у скрипта харнесса не должно быть
корнем проекта - рекурсия по рабочим каталогам дорогая (`.clinerules/40-lessons.md`, п.6).

### «Не удается загрузить файл ... не имеет цифровой подписи»

**Причина:** политика выполнения PowerShell запрещает скрипты.

**Лечение:** всегда добавлять `-ExecutionPolicy Bypass` (как во всех примерах), либо
разово:
```powershell
Set-ExecutionPolicy -Scope CurrentUser -ExecutionPolicy RemoteSigned
```

### Скрипт выводит «кракозябры» вместо русского текста

**Причина:** `.ps1` с русским текстом сохранён в UTF-8 **без BOM**, а Windows
PowerShell 5.1 читает такие файлы как ANSI.

**Лечение:** пересохранить файл в UTF-8 с BOM:
```powershell
Get-ChildItem 'scripts\*.ps1' | ForEach-Object {
  $c = Get-Content $_.FullName -Raw -Encoding UTF8
  [System.IO.File]::WriteAllText($_.FullName, $c, (New-Object System.Text.UTF8Encoding($true)))
}
```

### Долгая установка `install-mcp.ps1`

Венv сервера справки тянет `fastmcp`, `qdrant-client`, `grpcio` - это несколько
минут. Это нормально. Повторный запуск без `-Force` уже собранный venv не трогает.

## Внешняя интеграция (очередь задач)

Устройство слоя - `docs\07-external-integration.md`; состояние очереди в любой момент
показывает `py -3 integration\agent.py --list`.

### «Задача отправлена, но ничего не происходит»

**Причина:** не запущен watcher (`scripts\start-watcher.ps1` или `deploy\run-watcher.bat`) -
задачу с сервера забирает только он. Признак: в `scripts\check-harness.ps1` -
`[warn] замок watcher-а не обновлялся N с`, `GET /api/health` показывает `agents` пустым или
с устаревшей отметкой.

**Лечение:** поднять watcher фоном - `powershell -NoProfile -ExecutionPolicy Bypass -File
.\scripts\start-watcher.ps1`. Скрипт сам отвергает второй экземпляр: живой watcher виден по
процессам с `integration\watcher.py`. Если watcher был убит, замок `temp\queue\.watcher.lock`
снимается по возрасту через две минуты, а `scripts\start-watcher.ps1` снимает его сразу.

### «Watcher поднимали, а он не берёт задачи» (не тот сервер)

**Причина:** watcher смотрит на другой адрес или входит другим ключом. Очередь теперь одна -
на сервере, поэтому «другая папка» превратилась в «другой адрес».

**Лечение:** сверить `agent.server_url` и `agent.key` в `deploy\config.json` с
`server.public_url` и `server.clients`; проверить `py -3 integration\agent.py --health` - он
печатает счётчики очереди и агентов того сервера, к которому подключён.

### «Стадия delivered, а результата нет»

**Причина:** Cline не заполнил файл ответа или не вызвал `--write-result`. Стадия `delivered`
означает только то, что задача передана в Cline, и держится до записи итога.

**Лечение:** заполнить `temp\queue\<id>\answer.md` и выполнить
`py -3 integration\agent.py --write-result --task <id>`. Если ответ потерян совсем, дождитесь
`timeout_s` - сервер закроет задачу стадией `timeout`, и её можно поставить заново.

### «Задача отклонена»

**Причина:** формальная ошибка (схема), база вне `server.databases` или режим `harness` у
клиента без `allow_harness`. Настоящая проверка базы по `.v8-project.json` - уже на машине
агента.

**Где смотреть:** `failed\rejected_<id>.json` на сервере (задача и перечень ошибок) и ответ
`400` с полем `errors` - тексты те же.

### 401 и 413 в HTTP-интерфейсе

**401** - ключ не подошёл: его нет в `server.clients`, он передан без заголовка
`X-Integration-Token` (или `Authorization: Bearer`) либо относится к другому серверу.
**413** - тело больше предела `server.max_body` (по умолчанию 256 КБ): задача - это несколько
строк текста, поток в сокет очередь не обслуживает.

### URI не открывает задачу в Cline

**Причина:** протокол `vscode://` не связан с VS Code либо VS Code не запущен.

**Лечение:** работать режимами без GUI: `--deliver manual` печатает URI и строку запуска,
`--deliver echo` проверяет цепочку вообще без Cline.

### Страница задач не открывается

**Причина:** сервер не поднят (локально - `deploy\run-server.bat`, на хостинге - Passenger),
либо адрес открыт без базового URI (`/agent/`), либо в `server.clients` нет ключей - тогда
защищённые маршруты отвечают 503.

**Лечение:** проверить `GET <адрес>/api/health`: он отвечает без ключа и печатает счётчики
очереди и замечания настроек (`notes`). Если ответ 503 - задать `server.clients` в
`deploy\config.json`.

### Страница открылась, но поля пустые и кнопки не работают

**Причина:** `SyntaxError` в `integration\web\app.js` - файл внешне на месте, а браузер его
не исполняет (типичный след ручной правки: потерянная `}`). Ни `py_compile`, ни проверки
доков этого не видят.

**Лечение:** открыть консоль браузера (F12) и прочитать первую ошибку; синтаксис файла
проверяет `scripts\check-harness.ps1` (баланс скобок вне строк, комментариев и regex).
После правки перезагрузить страницу с очисткой кеша (Ctrl+F5).

## Отдельно: чего харнесс не умеет

- **Docker недоступен** - `1C_SyntaxChecker` и Docker-режим toolkit не работают.
- **1С 7.7 не установлена** - задачи по 77 невыполнимы.
- **Node.js и Java нет** - npm-обёртки и JVM-инструменты недоступны.
- **semantic-поиск** в справке платформы отключён (нужен `torch`).
- **Одна база за раз** - встроенный сервер 1C MCP Toolkit поднимается на одну
  информационную базу (`scripts\start-toolkit.ps1`; гасится `scripts\stop-toolkit.ps1`).
- **Запись в базу через toolkit** - при включённой защите обработки любой код с
  `Записать` отклоняется; снимается только флагом в форме `MCP_Toolkit.epf`.
- **Прогон сценариев Vanessa** - требует свободного клиентского слота в базе:
  прогону нужны два клиента одной ИБ (см. выше «Сценарий написан, но прогон не идёт
  или падает»). Сама обработка в конфигурацию не ставится: `scripts\vanessa-run.ps1`
  разворачивает её сам, а ключ `-FreeToolkit` освобождает базу от сеанса toolkit.
  Прогон - проверка **по требованию задачи**, а не обязательная проверка харнесса.
- **Стандартный интерфейс OData** - не настраивается автоматически: публикация
  поднимается скриптом, а состав объектов интерфейса задаётся в базе настройкой БСП.
- **Внешняя интеграция** - канал доставки задач, а не слой фактов: очередь последовательная
  (Cline ведёт одну задачу за раз), доставка URI работает только в Windows, состояние `queue\`
  в git не хранится (`docs\07-external-integration.md`).

## Контекст, префикс и схемы MCP

### «Авто-сжатие истории срабатывает часто, детали прошлых ходов теряются»

**Причина:** всегда-инжектируемый префикс (правила, `AGENTS.md`, метаданные скиллов, схемы
MCP-инструментов) занимает окно модели ещё до начала работы.

**Лечение:** посмотреть фактические числа - `powershell -File scripts\check-context.ps1`
(разбор по файлам и бюджетам; ключ `-Mcp` добавляет замер схем порта 6003). Разбор кейса из
правил переносится файлом в `analysis\`, в правилах остаётся инвариант. Тот же бюджет
проверяет `scripts\check-harness.ps1` в разделе «Промпт-бюджет».

### «В панели MCP лишние инструменты, и их схемы уходят в каждый запрос»

**Причина:** схема каждого инструмента (имя, описание, параметры) - часть запроса, поэтому
длинный хвост редких инструментов оплачивается постоянно.

**Лечение:** список `disabledTools` в `.cline/cline_mcp_settings.json` - по имени инструмента
(тот же механизм, что у галочек в панели MCP). После правки сервер надо переподключить в
панели: список инструментов клиент сам не перечитывает. Замер - временные пробы
`temp\probe-tools.ps1` (HTTP) и `temp\probe-stdio.py` (stdio-серверы); перечень отключённого
и причина - `docs\04-mcp-servers.md`.

### Схемы MCP измеряются неправильно: «одна строка ответа» и кракозябры

**Причина:** ответ MCP по HTTP приходит как SSE, и одно событие может состоять из
нескольких строк `data:`. Построчный разбор как JSON теряет список инструментов или
обрезает его. Отдельно: тело запроса и ответ надо отдавать и читать как UTF-8
(`RawContentStream`), иначе кириллица приходит кракозябрами.

**Лечение:** склеивать все строки `data:` одного события до пустой строки (так делает
`scripts\check-context.ps1` с ключом `-Mcp`), а тело `ConvertTo-Json` отдавать байтами UTF-8.

### «Русского текста в правилах много, а экономить надо»

**Факт:** кириллица в токенизаторах плотнее латиницы: символ русского текста стоит примерно
вдвое дороже символа английского. Сокращать надо не язык, а объём: инвариант вместо разбора,
указатель вместо пересказа. Порядок цен в префиксе - схемы MCP-инструментов, затем правила,
затем метаданные скиллов; `README.md`, `docs\`, `analysis\` не инжектируются вообще.
