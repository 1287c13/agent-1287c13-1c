# Архитектура решения

## Что построено

Харнесс, превращающий Cline в 1С-агента. Три составляющие, все - внутри каталога
репозитория `C:\_works\1c-ai\agent` (он же рабочее место агента):

1. **Контракт.** `START.md`, `AGENTS.md`, `.clinerules/*` - задают единый формат
   задачи, обязательную преамбулу, запрет на выдумывание и обязательную проверку.
2. **Возможности.** Три MCP-сервера (`.cline/mcp/`) и 206 скиллов
   (`.cline/skills/`) от шести вендоров.
3. **Эксплуатация.** Скрипты установки, запуска и диагностики (`scripts/`).

## Поток выполнения задачи

```
пользователь
   |  «как <роль> сделай <действие> в базе <база> чтобы <цель> по START.md»
   v
Cline (VS Code)
   |  читает правила:  AGENTS.md + .clinerules/*            <- контракт
   |  под закачку:     .cline/skills/*/SKILL.md             <- процедуры
   v
преамбула Слой / MCP / Скиллы / Проверка
   |
   +--> MCP 1c-toolkit        (живая база: данные, код, метаданные, OData)
   +--> MCP 1c-code-index     (структура и связи по выгрузке)
   +--> MCP 1c-platform-help  (сигнатуры API, стандарты BSL)
   +--> скиллы                (сборка/разбор/валидация, Gherkin, публикация)
   v
проверка (повторный MCP-вызов / валидатор скилла / загрузка в базу)
   v
отчёт  «Сделано / Проверка / Не проверено»
```

## Почему именно так

**Cline читает project-скиллы, но не project-MCP.** Обратное проектирование
`dist/extension.js` расширения показало:

- скиллы: `.cline/skills`, `.claude/skills`, `.clinerules/skills`, `.agents/skills`;
- правила: `.clinerules`, `.cursor/rules`, `.cursorrules`, `AGENTS.md`;
- MCP: только глобальный `cline_mcp_settings.json`, каталог задаётся переменными
  `CLINE_MCP_SETTINGS_PATH` -> `CLINE_DATA_DIR\settings\...` -> `CLINE_DIR\data\settings\...`.

Поэтому скиллы и правила кладутся в проект напрямую, а MCP - через переменную
окружения, указывающую на файл внутри проекта. Это единственная точка, выходящая
за пределы каталога.

**Cline не понимает cursor-семантику `globs`/`alwaysApply`.** Строки `alwaysApply`
в `extension.js` нет. Значит, любой подключённый файл-правило становится
постоянным. 40 вендорских `.mdc`-правил в таком режиме раздули бы контекст на
сотни килобайт, поэтому они оставлены справочником и читаются по одной под задачу.
В `.clinerules/` лежат только шесть коротких операционных файлов.

**Слои разделены по источнику факта.** Данные - только из живой базы, структура
кода - только из индекса, сигнатуры - только из справки платформы. Это прямое
следствие требования «прекрасно работает»: агент, отвечающий по памяти, ошибается
на именах, и ошибку видно только в базе.

## Состав каталогов

```
1c-ai/agent/                       корень харнесса (он же корень рабочего места)
├── START.md                       протокол (точка входа для агента)
├── AGENTS.md                      краткая выжимка контракта
├── README.md                      инструкция для человека
├── SOURCES.md                     внешние источники и их версии
├── .clinerules/                   постоянные правила
│   ├── 00-contract.md             формат задачи, преамбула, запреты
│   ├── 10-mcp-and-skills.md       карта инструментов и слоёв
│   ├── 20-1c-platform.md          базы, платформы, кириллица, ограничения
│   ├── 30-verification.md         чем и как проверять
│   ├── 40-lessons.md              грабли и уроки (дописывается по ходу работы)
│   └── 50-harness.md              работа по самому харнессу (задачи без базы)
├── .cline/
│   ├── cline_mcp_settings.json    конфигурация трёх MCP-серверов
│   ├── mcp/                       бинарники серверов (не в git)
│   │   ├── code-index-mcp/        bsl-indexer.exe + home/daemon.toml
│   │   ├── 1c-mcp-toolkit/        MCP_Toolkit.epf
│   │   └── bsl-platform-help-context/  venv + mcp-bsl-context.exe
│   └── skills/                    206 скиллов (собираются из skills-vendor, не в git)
├── .v8-project.json               базы и путь к платформе 1С
├── analysis/                      результаты анализа агента: разборы кейсов и расследования,
│                                  имя файла - метка времени плюс краткое имя (в git не хранятся)
├── docs/                          описание решения
├── mcp/                           доки и пример конфигурации по MCP-серверам
├── scripts/                       install / start / check / publish + start-toolkit / stop-toolkit / vanessa-run / new-analysis
├── temp/                          временные файлы задач, включая сценарии .feature (в git не хранится)
└── skills-vendor/                 вендорские репозитории (в git не хранятся)
```

## Что не входит в решение и почему

| Отброшено | Причина |
|-----------|---------|
| `1C_SyntaxChecker` | требует Docker; на машине его нет |
| Docker-режим `1C MCP Toolkit` | требует Docker; используется встроенный сервер |
| `77MCP` | на машине нет платформы 1С 7.7 |
| `mcp-remote` / npm-обёртки | на машине нет Node.js |
| `ai-edt`, `1c-naparnik` | требуют 1С:EDT / внешнего сервиса, не подтверждены на машине |
| semantic-режим сервера справки | требует `torch` и модели-эмбеддера (гигабайты); keyword-режима достаточно |
