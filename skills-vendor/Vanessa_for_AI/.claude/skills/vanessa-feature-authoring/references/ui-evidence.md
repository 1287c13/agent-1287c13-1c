# Доказательства UI-фактов

## Допустимые источники

Используй UI-деталь только когда она подтверждена одним из источников:

1. запись пользователя из текущего окружения;
2. runtime-диагностика текущего запуска;
3. runtime-проверенный сценарий той же формы и версии;
4. ближайший README, где явно указана версия и успешный прогон.

Каталог стандартных шагов не является источником имён элементов конфигурации.

## Не выводить одно из другого

- Заголовок списка, заголовок формы элемента и подпись панели открытых различаются.
- Имя поля формы не доказывает существование одноимённой колонки списка.
- Доступное значение не доказывает, что работает конкретный способ выбора.
- Похожий объект не доказывает одинаковое поведение форм.
- Заголовок до записи не доказывает заголовок после записи.

## Сохранять способ взаимодействия

Не заменяй без нового доказательства:

- прямой ввод выбором из списка;
- `я выбираю по строке` выбором точного значения;
- форму выбора контекстным поиском;
- поиск `Найти` переходом к строке таблицы;
- записанное действие «подготовки» упрощённой последовательностью.

Если два источника расходятся, покажи конфликт и спроси, какой наблюдался в текущем окружении.

## Динамические имена TestClient

Для имён вида `Поле<GUID>` не считай префикс частичным совпадением штатного `НайтиОбъект`. Если запись подтверждает динамическое имя:

1. получи содержащую таблицу формы;
2. найди её поля через TestClient API;
3. фильтруй по всем подтверждённым устойчивым свойствам;
4. потребуй ровно одно совпадение;
5. работай с найденным UI-объектом напрямую;
6. не помещай UI-объекты в сериализуемый контекст.
