# Product Manager / Analyst — Claude Skill

**Claude-ის სქილი (Agent Skill), რომელიც Claude-ს სენიორ პროდუქტ-მენეჯერად და ბიზნეს-ანალიტიკოსად აქცევს — ქართულად საუბრით, სტანდარტების შესაბამისი მოთხოვნებით და ERP/1C დანერგვის სპეციფიკის ცოდნით.**

> **English:** A Claude Agent Skill that turns Claude into a senior product manager and business analyst. It runs discovery, prioritizes, writes PRDs and formal specifications (ГОСТ 34.602, ISO/IEC/IEEE 29148), produces user stories with acceptance criteria, models processes and data, defines metrics and OKRs, and handles stakeholder work — with deep coverage of ERP and 1C:Enterprise implementation analysis. All prose and deliverables in fluent Georgian.

---

## რას აკეთებს

სქილი სამ რეჟიმში მუშაობს:

- **აღმოჩენა (Discovery)** — როცა პრობლემა ჯერ არ არის დადგენილი, ან მოთხოვნა მოვიდა როგორც მზა გადაწყვეტა. მომხმარებელთა ინტერვიუები ქცევაზე (და არა განზრახვაზე), შესაძლებლობების რუკა, რისკიანი დაშვებების გამოვლენა და იაფი შემოწმება, პრიორიტიზაცია RICE / ICE / MoSCoW / Kano / WSJF / opportunity scoring-ით — **ყოველთვის იმის თქმით, რას ვერ ხედავს არჩეული მეთოდი**.
- **სპეციფიკაცია (Specification)** — PRD და პროდუქტის ბრიფი, ТЗ ГОСТ 34.602-2020-ით, SRS ISO/IEC/IEEE 29148-ით, ФТ და ЧТЗ, მომხმარებლის ისტორიები მიღების კრიტერიუმებით, ბიზნეს-პროცესების და მონაცემთა მოდელირება, постановка задачи 1C-ის დეველოპერისთვის, მიღების სცენარები.
- **რევიუ (Review)** — არსებული დოკუმენტის აუდიტი: მოთხოვნების ხარისხი, სისრულე, გადამოწმებადობა, მოდელები, პრიორიტეტები და ERP-სპეციფიკა. შედეგი სიმძიმის დონეებად: 🔴 კრიტიკული / 🟠 მნიშვნელოვანი / 🟡 მცირე / 🟢 რეკომენდაცია — ციტირებული ტექსტით და კონკრეტული შესწორებით.

### სამი ნაბიჯი

ყოველი არსებითი დავალება გადის სამ ეტაპს: **პრობლემა და კონტექსტი → დოკუმენტი → გადამოწმება და მიღების კრიტერიუმები.** მესამე ნაბიჯი სწორედ ის არის, რაც ანალიტიკოსების გამომუშავებას ყველაზე ხშირად აკლია — და რის გამოც სპეციფიკაციების მიხედვით მიღება შეუძლებელი ხდება.

### მთავარი წესი: ბიზნეს-ფაქტი არ გამოიგონება

ანალიტიკოსის დამახასიათებელი ჩავარდნა არ არის ცუდი წერა — ეს არის დამაჯერებელი გამოგონილი დეტალი, რომელსაც ვერავინ ამჩნევს და რომელზეც შემდეგ ყველა აშენებს. სქილი უცნობს ნიშნავს `[დასაზუსტებელია: რა, ვინ პასუხობს]`-ით და აგროვებს ღია კითხვების სექციაში პასუხისმგებლითა და ვადით. **თხუთმეტი პატიოსანი ხარვეზის მქონე დოკუმენტი გამოსადეგია — ხარვეზებს ხურავენ. თხუთმეტი გამოგონილი მნიშვნელობით — არა, და ის უკეთესად გამოიყურება.**

### ERP / 1C: გადაწყვეტილება, რომელიც ყველაზე ძვირია

ტიპური კონფიგურაციის დანერგვისას ერთი გადაწყვეტილება განსაზღვრავს პროექტის ეკონომიკას, და ის ანალიტიკოსისაა და არა დეველოპერის:

```
0. ბიზნეს-პროცესის შეცვლა ტიპურის ქვეშ          ← ყოველთვის განიხილე პირველად
1. პარამეტრიზაცია                                → მხარდაჭერა ხელუხლებელი
2. გარე ობიექტები (.epf / .erf)                  → მხარდაჭერა ხელუხლებელი
3. კონფიგურაციის გაფართოება (.cfe)               → კონფიგურაცია რჩება „ჩაკეტილი"
4. ტიპური ობიექტის ცვლილება მხარდაჭერით          → ხელით გაერთიანება ყოველ რელიზზე
5. ახალი საკუთარი ობიექტი                        → იგივე რეჟიმი, რაც 4-ში
6. მხარდაჭერიდან სრული მოხსნა                    → განახლება მხოლოდ დეველოპერებით
```

3-დან ქვემოთ თითოეული ნაბიჯი ზრდის **ყოველი მომავალი განახლების** ღირებულებას (დონეები 4 და 5 ერთ მხარდაჭერის რეჟიმშია; გადამწყვეტია, რამდენ ტიპურ ობიექტს ეხები ხელით). სქილმა ეს ხმამაღლა უნდა თქვას — სპონსორი წინადადებებს ადარებს, განსხვავება კი მფლობელობის სრულ ღირებულებაშია და არა ფასში.

### ენობრივი წესი

- **მთელი პროზა და თავად დელივერებლები — ქართულად:** გეგმები, ანალიზი, PRD, სპეციფიკაცია, ისტორიები, მიღების კრიტერიუმები, რევიუს დასკვნები.
- **კანონიკური ტერმინები რჩება ორიგინალში**, ქართულ ახსნასთან ერთად: `მიღების კრიტერიუმები (acceptance criteria)`, `ხარვეზების რეესტრი (реестр GAP)`.
- **იდენტიფიკატორები არასოდეს ითარგმნება:** `Документ.РеализацияТоваровУслуг`, `ГОСТ 34.602-2020 §4.6.2`, `R-014`.

## გამოყენების მაგალითები

```
კლიენტს უნდა, რომ გაყიდვების შეკვეთა ავტომატურად დაიბლოკოს, თუ
კონტრაგენტს საკრედიტო ლიმიტი აქვს ამოწურული. დაწერე постановка задачи.
```
→ სქილი ჯერ დააზუსტებს პრობლემას და გაზომვად შედეგს, შემდეგ შეაფასებს ტიპურ ფუნქციონალს (1C:ERP-ს უკვე აქვს კრედიტის კონტროლი), აჩვენებს რეალიზაციის დონეს და მის ფასს მხარდაჭერისთვის, და მხოლოდ ამის შემდეგ დაწერს ЧТЗ-ს რეკვიზიტების ცხრილით, გატარების ალგორითმით, უფლებებით და საკონტროლო მაგალითით.

```
ეს არის ჩვენი ТЗ. გადახედე.
```
→ რევიუ-რეჟიმი: ჟანრის დადგენა → მოთხოვნების ხარისხი → სისრულე → გადამოწმებადობა → ERP-სპეციფიკა, დასკვნები სიმძიმის დონეებად, ციტირებული ტექსტით და კონკრეტული შესწორებით.

```
ოცი მოთხოვნაა და ორი თვე. როგორ დავალაგო?
```
→ ჩარჩოს არჩევა სიტუაციის მიხედვით (ფიქსირებული ვადა → MoSCoW 60%-იანი წესით), ქულების ცხრილი ყველა შემავალი მონაცემით, რანჟირება დასაბუთებით, ცხადი „Won't this release" და — სავალდებულოდ — რას ვერ ხედავს არჩეული მეთოდი.
