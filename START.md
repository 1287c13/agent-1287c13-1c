# START.md — протокол работы 1C-агента

Файл-точка входа. Читается агентом в начале **каждой** задачи, поставленной в
едином формате. Здесь - формат, протокол и что считается результатом.

Полная инструкция для человека - [README.md](README.md).
Устройство решения - [docs/01-architecture.md](docs/01-architecture.md).

---

## 1. Единый формат задачи

```
как <роль> сделай <действие> в базе <база> чтобы <цель> по START.md
```

| Слот | Значение | Пример |
|------|----------|--------|
| `как <роль>` | область ответственности | `как программист 1С`, `как тестировщик`, `как аналитик` |
| `сделай <действие>` | что сделать | `напиши Gherkin-тест и запусти его` |
| `в базе <база>` | информационная база | `File="C:\Users\art8k\...\DemoARAutomation20"`, `демо`, `erp` |
| `чтобы <цель>` | критерий готовности | `чтобы документ проводился с комментарием Hello world` |
| `по START.md` | маркер протокола | читать этот файл и следовать ему |

Задача, пришедшая не в этом формате, не выполняется: агент просит переформулировать.

### 1.1. Второй формат - задача по самому харнессу

Задача бывает про инструмент агента, а не про базу 1С. Тогда база в ней не пишется:

```
как инженер харнесса сделай <действие> чтобы <цель> по START.md
```

Различение: названа база 1С - задача по базе; правится инструмент агента (правило,
скрипт, док, формат задачи) - задача по харнессу. Подробности и границы -
`.clinerules/50-harness.md`.

## 2. Что делает агент

1. Читает `START.md` (этот файл) и `.clinerules/*`.
2. Разбирает слоты. Базу разрешает по `.v8-project.json`.
3. Печатает преамбулу:

```
Слой: <слой решения>
MCP: <инструменты, которые будут вызваны>
Скиллы: <скиллы, которые будут прочитаны>
Проверка: <чем подтвердится результат>
```

4. Выполняет задачу, используя MCP-серверы и скиллы (карта - `.clinerules/10-mcp-and-skills.md`).
5. Проверяет результат (`.clinerules/30-verification.md`) и отчитывается:

```
Сделано: ...
Проверка: ...
Не проверено: ...
```

---

## 3. Три слоя, из которых собирается решение

| Слой | Что даёт | Где |
|------|----------|-----|
| **Живая база** | данные, выполнение кода, метаданные, OData - **факты о базе сейчас** | MCP `1c-toolkit`, `http://127.0.0.1:6003/mcp` |
| **Индекс кода** | структура и связи по выгрузке, поиск процедур - **статический анализ** | MCP `1c-code-index` |
| **Скиллы + справка** | процедуры, форматы, валидаторы, сигнатуры API | `.cline\skills\`, MCP `1c-platform-help` |

Правило выбора: факт о том, **что лежит в базе**, берётся только из живой базы.
Факт о том, **как устроен код**, - из индекса. Факт о том, **существует ли метод
платформы**, - из справки. Ничего из этого не берётся «по памяти».

## 4. Пример: рабочая задача целиком

Задача пользователя:

```
как тестировщик 1С сделай Gherkin-тест и запусти его в базе
File="C:\Users\art8k\OneDrive\Документы\1C\DemoARAutomation20",
чтобы документ с комментарием проводился, вернулись первые 10 наименований
справочника ОбъектыЭксплуатации и список опубликованных метаданных OData
по START.md
```

Что делает агент:

1. **Преамбула.**
   ```
   Слой: живая база + скиллы (Vanessa/Gherkin), индекс кода для выбора документа
   MCP: 1c-toolkit (get_metadata, execute_query), 1c-code-index (get_object_structure)
   Скиллы: va-scenario-generator, Vanessa_for_AI, 1c-db-run, web-publish
   Проверка: повторный get_metadata/execute_query по OData и по документу
   ```
2. Разрешает базу: `demo-ar` из `.v8-project.json` (совпадает с указанным путём).
3. Находит документ с реквизитом `Комментарий` - через `1c-toolkit` `get_metadata`
   (не «по памяти»).
4. Пишет `.feature` и кладёт его рядом с проектом.
5. Запускает сценарий в базе внешней обработкой Vanessa (`scripts\vanessa-run.ps1`) и проверяет факт записи
   комментария и проведения документа повторным чтением.
6. Читает первые 10 наименований `Справочник.ОбъектыЭксплуатации` запросом.
7. Поднимает OData (скилл `web-publish`) и возвращает разбор ответа запроса
   к опубликованным метаданным.
8. Отчитывается в формате «Сделано / Проверка / Не проверено».

### Известные ограничения этой базы (проверяются до работы, см. `.clinerules/40-lessons.md`)

| Ограничение | Как проверяется заранее | Что это значит |
|---|---|---|
| Прогону нужны два клиента базы (лицензия) | есть ли чужие клиентские сеансы той же базы, в том числе сервер toolkit на 6003 | платформа отвечает `Превышено ограничение лицензии ...`; сеанс toolkit прогон гасит и возвращает сам (`-FreeToolkit`), чужие окна 1С закрывает человек |
| Обработка Vanessa развёрнута | есть ли `.vanessa\vanessa-automation-single.epf` | развернёт сам `scripts\vanessa-run.ps1` из релизного архива; в конфигурацию базы Vanessa не ставится - запускается внешней обработкой. Прогон - по требованию задачи, не обязательная проверка |
| Запись через `1c-toolkit` закрыта защитой | попытка `execute_code` вернёт «Операция запрещена: код содержит опасные ключевые слова» | шаги «записать комментарий», «провести документ» через MCP не выполняются до снятия флага в форме обработки |
| OData публикуется, но метаданные не отдаются | `GET <адрес>/odata/standard.odata/$metadata` → 404 при 200 на корне | стандартный интерфейс OData в КА2 не настроен (пустая `ПользовательСтандартногоИнтерфейсаOData`); публикация - `scripts\publish-odata.ps1` |

Эти ограничения не отменяют задачу: агент выполняет то, что выполнимо (сценарий,
справочник, публикацию), и называет невыполненное в отчёте, а не ищет обходные пути.

## 5. Что считается нарушением протокола

- работа без преамбулы;
- выдуманный факт (имя объекта, реквизита, метода);
- выдуманный MCP-инструмент;
- собственный скрипт вместо существующего скилла или MCP-инструмента;
- «должно работать» вместо проверки;
- утверждение об успехе, когда средство проверки не вызывалось;
- **подмена приоритета**: инфраструктурные действия (публикация базы, настройка OData,
  подъём сервисов) в задаче, где просили артефакт, и собственные скрипты «по пути»;
- **знание, не перенесённое в правила**: найденное ограничение не описано в
  `.clinerules/40-lessons.md` или `docs/06-troubleshooting.md`;
- **задача по харнессу решена без проверки**: не прогнаны `scripts\check-harness.ps1`
  и `scripts\check-docs.ps1` до и после правки;
- **временные файлы вне `temp\`**: разовые скрипты, логи, выгрузки ответов и черновики по
  задаче хранятся только в `temp\` (каталог в `.gitignore`);
- **повторный подъём живого слоя**: `scripts\start-toolkit.ps1` не запускает второй клиент,
  если сервер уже отвечает или сеанс с обработкой уже есть; повторный запуск - только `-Force`.

## 6. Перед первой задачей

Харнесс должен быть поднят. Проверка одной командой:

```powershell
# жив ли харнесс: установлено, запущено, чего не хватает
powershell -NoProfile -ExecutionPolicy Bypass -File .\scripts\check-harness.ps1

# не разошлись ли доки с фактами (числа скиллов, пути, имена инструментов)
powershell -NoProfile -ExecutionPolicy Bypass -File .\scripts\check-docs.ps1
```

Живой слой (MCP `1c-toolkit`) поднимается скриптом: `scripts\start-toolkit.ps1` открывает
обработку в базе из `.v8-project.json` и включает встроенный сервер (гасится
`scripts\stop-toolkit.ps1`). Скрипт идемпотентен: если `/health` уже отвечает или сеанс 1С
с обработкой запущен, второй клиент не поднимается. Ежедневный запуск - `scripts\start-harness.ps1`.
Временные файлы задач - только в `temp\`.

Если что-то не так - [README.md](README.md), раздел «Установка».
